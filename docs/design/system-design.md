# 系统设计推演

> **这份文档是干什么的**
>
> 它不是"系统现在长什么样"的说明书（那是 [`docs/architecture/`](../architecture/)），也不是"接下来做什么"的计划（那是 [`docs/plans/`](../plans/) 和 [`docs/tasks/`](../tasks/)）。
>
> 它回答一个问题：**从"要卖座位"这个需求出发，怎么一步步推导出现在这些技术选择。**
>
> 目标是让我在半年后遇到一个诡异 bug 时，能凭这份文档判断"这是设计如此，还是坏了"——而不是对着代码猜。

---

## 阅读约定

**规模前提**：全文的推理建立在一组**假想的业务规模**上（见第 1 章）。这个规模不是当前实测数据，是"修完已知缺陷、补完配置后，这台开发机上真能压出来"的目标。选它是因为：规模太小，一半的设计会显得没有动机；规模太大，推出的结论和这个仓库永远对不上。

**每个重大决定按这个模板展开**：

| 栏 | 内容 |
|---|---|
| **S · 处境** | 业务处境，用规模数字说话 |
| **T · 要求** | 由此产生的技术要求，区分硬要求（不可妥协）和软要求（可权衡） |
| **A · 做法** | 怎么做的，以及**为什么不是别的方案**——这是全文最重要的一栏 |
| **R · 代价与边界** | 付出了什么、在什么条件下失效。**不写好处**，好处只是把 T 重复一遍 |
| **📍 当前实现** | 代码做到哪一步，带文件和行号。**全篇唯一会随代码腐烂的部分** |
| **🔧 可以更好** | 格式固定为「当 X 成立 → 改为 Y → 代价是 Z」。写不出代价的不写 |

**边界**：这份文档不列任务、不排优先级、不排阶段。已登记的缺陷只引编号（`D-xx`），不重述内容——重述一遍，等 D-06 修完之后这里就会有一处永久说谎的文字。

**关于 SLO**：文中出现的 SLO 数字是**目标值**。`metrics-report.json` 里的 4.86ms 是一次旧测量，只作参考，不作论据。

**字段级的"为什么"**（为什么用 UUID、为什么金额用 BIGINT）不套 STAR，集中在附录，因为它们的理由是跨表共享的。

# 第 1 章：这个系统服务于谁

> 本章不套 STAR 模板——**它本身就是全文的 S 和 T**。后面每一个决定的"处境"和"要求"，都是从这一章推出来的。

## 1.1 谁在用，用来干什么

两类角色：

| 角色 | 干什么 | 走哪条路 |
|---|---|---|
| **旅客** | 搜航班 → 看详情 → 下单 → 查订单 → 取消 | 全部 6 个 REST 端点 |
| **票务运营** | 录入航班、调价、改航班状态 | **当前不存在**——航班数据只能靠迁移里的 seed 写入 |

第二类角色的缺席不是疏漏，是有意的范围裁剪：这个系统要练的是**高并发下的库存正确性**，不是后台管理。但它有个后果值得记住——**没有任何一条代码路径会修改 `flights.price` 和 `flights.status`**，所以"改价之后已有订单怎么办""航班取消之后订单怎么办"这两个问题在当前实现里从未被触发过。它们不是已解决，是没遇到过。

## 1.2 核心资源：座位

整个系统只有一种真正稀缺的资源——**座位**。它有四个性质，这四个性质决定了后面所有的技术选择：

1. **有限且不可超卖**。库存卖多了不是"数据不一致"，是**航司要给旅客赔钱、要安排改签**。这是硬约束，不能用"最终一致"糊弄过去。
2. **可归还**。取消订单要把座位还回池子，所以库存不是单调递减，而是有增有减——这让"归还两次"变成一个真实的风险（见 5.5）。
3. **热点极度集中**。不是"整个系统 2000 QPS"，而是"**2000 QPS 全部砸在一个航班上**"。这个区别是致命的：分散负载可以靠加机器解决，集中负载不行。
4. **单位价值高、单笔金额大**。所以金额不能用浮点数，价格要在下单时快照（见附录、第 4 章）。

> 对照一下：如果这个系统卖的是"点赞数"，上面四条一条都不成立，那么整个架构可以是无锁的、最终一致的、缓存直接当真相。**难度不来自技术，来自资源的性质。**

## 1.3 假想规模

这组数字是全文推理的起点。

| 维度 | 数字 |
|---|---|
| 日订单量 | **20 万**（平均 2.3 单/s） |
| 平峰请求量 | **500 QPS**，读写比约 20:1 |
| 放票尖峰 | 每天固定时刻放票，**60 秒内 2000 QPS** |
| 尖峰的形状 | **下单请求几乎全部集中在 1 个航班上**——3 万人抢 300 个座位 |
| 单航班座位数 | 300 |

**为什么是这组数字**：这台开发机是 12 vCPU / 7.7 GiB 内存，跑着 13 个容器且没有资源限制。按这个配置推算——读路径约 2000–3000 QPS 可达，写路径分散时约 300–600 单/s 可达，而**同一个航班的写入上限约 300–1000 单/s**（推导见第 5 章）。

所以这组数字被刻意设计成**一半够用、一半不够用**：

- **平峰 500 QPS**：当前架构轻松扛住 → 证明现有设计在正常态不是过度设计
- **尖峰 2000 QPS 打单航班**：必然撞穿行锁上限 → 证明库存扣减这条路必须改造

一份文档里同时有"够用"和"不够用"两个结论，方向感才是真的。而且这两个场景 k6 在这台机器上都能压出来——**不用信推算，可以亲手测到拐点**。

## 1.4 由规模推出的四条要求

这四条是后面每一章反复引用的源头。

| # | 要求 | 硬/软 | 来自 |
|---|---|---|---|
| **R1** | **超卖 = 0** | 硬，不可妥协 | 1.2 座位的性质 1 |
| **R2** | 平峰 p95 < 50ms，尖峰 p95 < 500ms | 软，可权衡 | 1.3 规模 |
| **R3** | 尖峰错误率 < 1%（不含"座位卖完"这种正常业务拒绝） | 软 | 1.3 规模 |
| **R4** | 单点故障不导致整体不可用；下游挂掉时上游要能快速失败而不是拖死 | 硬 | 1.3 尖峰下故障放大 |

注意 **R1 和 R2/R3 是会打架的**：保证绝不超卖最简单的办法是把所有下单串行化，但那样尖峰下延迟会爆炸。全文大部分设计取舍，本质上都是在这条冲突线上选位置。

## 1.5 为什么"卖座位"天然是分布式系统的好练习题

| 难点 | 在这个系统里的体现 | 在哪一章 |
|---|---|---|
| 有限资源的并发竞争 | 最后一个座位被两个人同时抢 | 第 5 章 |
| 跨服务状态一致性 | 订单在 A 库、库存在 B 库，没有分布式事务 | 第 5 章 |
| 缓存一致性 | 座位数变了，缓存里的旧值怎么办 | 第 6 章 |
| 失败传播 | 下游挂了，上游是等死还是快速失败 | 第 7 章 |
| 热点与削峰 | 2000 QPS 砸在一行数据上 | 第 5 章、第 7 章 |

### 📍 当前实现

- 数据库里只有 **3 个 seed 航班**（`flight-service/migrations/002_seed.up.sql`），k6 脚本从这 3 个 UUID 里随机挑（`k6/script.js:19-23`）。也就是说**当前压测的热点分散度是 1/3，不是 1/1**——离尖峰场景差得远。
- **这个系统的吞吐上限从未被测过。** 唯一一次基线（`docs/reports/load/2026-05-29-baseline.md`）跑出 82.86 req/s，但脚本里有 `sleep(0.1)`（`k6/script.js:82`），10 VU ÷ 0.11s ≈ 90/s——**测到的是 k6 自己的天花板，不是系统的**。中位数 0.92ms 说明当时系统基本闲着。
- 没有航班管理能力，`price` / `status` 在运行期不会被任何代码修改。

### 🔧 可以更好

- **当需要验证"尖峰打单航班"这个场景时** → k6 脚本增加一个 scenario：去掉 `sleep`、VU 提到 200+、`FLIGHTS` 数组固定成单个 UUID，观察 `available_seats` 归零前后的 p99 曲线和错误码分布。**代价**：压测机与被测服务同机，200 VU 的 k6 会和 13 个容器抢 CPU，测出来的延迟里混着压测机自己的排队——这台机器上区分不开，只能把结论限定为"拐点在哪"而不是"绝对延迟是多少"。相关：D-16。
- **当要验证"改价后已有订单不受影响"时** → 需要先有一条修改 `flights.price` 的路径（哪怕是个内部 gRPC 方法）。**代价**：新增写路径就要新增它自己的并发控制和缓存失效，范围会外溢到第 5、6 章。

# 第 2 章：架构为什么是这个形状

本章四个重大决定：拆两个服务、分两个库、内部用 gRPC、外部单一入口。

它们看起来是四个决定，其实是**一个决定的四个面**——第一个决定做完，后面三个基本被锁死了。这一点本身就值得记住：架构决策的成本不在于它本身，在于它锁死了多少后续选项。

## 2.1 为什么拆成两个服务

**S · 处境**
系统要同时管两类东西：**订单**（谁买的、买了几个、花了多少钱）和**库存**（这个航班还剩几个座位）。尖峰时 2000 QPS 里绝大多数是读航班，下单只占一小部分，但下单是唯一会争抢库存的操作。

**T · 要求**
- R1（超卖=0）要求库存的修改必须**有唯一的仲裁者**——两个地方都能改库存，就没有任何一种锁能保证正确
- 读航班和写订单的负载特征完全不同（读可缓存、写不可缓存），要能分别演进和扩容

**A · 做法**
拆成 `booking-service`（订单所有权方，对外 REST）和 `flight-service`（航班与座位所有权方，仅内部 gRPC）。座位的任何增减**只能**通过 flight-service。

*为什么不是单体*：单体在当前规模下**完全够用**，而且少一次网络跳转、少一整套韧性代码、`CreateBooking` 可以在一个本地事务里完成——第 5 章那个跨库一致性缺口（D-06）在单体里根本不存在。选择拆分付出的是真金白银的复杂度，换来的是所有权边界清晰和独立扩容能力。**必须诚实承认：在 20 万单/日这个规模上，这笔交易是亏的。** 它值得的前提是"读流量和写流量的增长速度差异大到需要分别扩容"，而这个前提当前并不成立。

*为什么不是按"读/写"拆（CQRS）*：那样库存的写入方仍然需要一个唯一仲裁者，问题原封不动，只是换了个位置。

*为什么不是按"用户/航班/订单"拆三个*：用户域当前只有一个 `user_id` 字段，拆出来是空服务。**服务边界应该沿着"数据所有权"划，不是沿着名词划。**

**R · 代价与边界**
- 每次下单多两次网络往返（`GetFlight` + `ReserveSeats`），在 R2 的延迟预算里占一部分
- **产生了一个跨库一致性缺口**：扣库存成功、写订单失败，座位就泄漏了（D-06）。这是拆分直接买来的问题
- 需要一整套跨服务韧性机制（重试、熔断、认证），这些代码在单体里一行都不需要
- 失效边界：服务数量继续增长时，这种"点对点 gRPC + 各自韧性逻辑"的模式会退化——每加一个服务，韧性配置的组合数增长，此时需要服务网格或统一的调用框架

**📍 当前实现**
- 边界执行得很干净：`booking-service` 全仓库**没有任何一处直接连 `flight_db`**，所有座位操作都走 `grpcclient`
- 两个服务的分层结构一致：`handler → service → repository`，依赖方向单向
- `booking-service` 依赖了 `flight-service` 的生成代码包（`booking-service/internal/service/booking.go:12` 直接 import `flight-service/pb/flight`）——两个服务共享一个 Go module 边界，**契约的物理隔离没有做到**

**🔧 可以更好**
- **当两个服务需要独立发版、或者要给第三方提供客户端时** → 把生成的 pb 代码拆成独立模块（或独立仓库），双方按版本号依赖。**代价**：改一次 proto 要走"发布 pb 版本 → 升级依赖 → 两边各自发版"三步，本地开发的迭代速度会明显变慢；当前单仓库改完 `make proto` 就能跑。在只有一个开发者的情况下这笔交易是亏的。

## 2.2 为什么两个独立数据库

**S · 处境**
拆服务之后，数据放哪：共享一个库，还是各持一个。

**T · 要求**
- 服务边界要真实——如果两个服务都能读写同一张表，"所有权"就只是口头约定
- R1（超卖=0）要求库存的并发控制手段统一

**A · 做法**
`flight_db`（`flights`、`seat_reservations`）和 `booking_db`（`bookings`）完全分离，**没有跨库外键**。`bookings.flight_id` 和 `seat_reservations.booking_id` 是逻辑引用，数据库层面无法校验。

*为什么不是共享库*：共享库最大的诱惑是——`CreateBooking` 可以在**一个本地事务**里完成扣库存和写订单，D-06 那个一致性缺口直接消失。这个诱惑很大。否决它的理由是：共享库会让"谁能改这张表"重新变成口头约定，而口头约定在并发场景下等于没有约定。一旦 booking-service 某天为了省一次 RPC 直接 `UPDATE flights`，`FOR UPDATE` 的锁就保护不了跨服务的竞争了——**而这种"抄近道"在压力下几乎必然发生**。

*为什么不是同一个 PostgreSQL 实例里的两个 schema*：那样物理上还是一个数据库，一个慢查询会拖垮另一个服务，故障域没有隔离。不过它确实能省一个容器和一份内存——在这台 7.7 GiB 的机器上不是小数目。

**R · 代价与边界**
- **跨库一致性只能靠应用层保证**，数据库帮不上忙（第 5 章展开）
- 无法用 `JOIN` 查"这个订单对应的航班信息"，必须两次调用后在应用层拼接
- 两个 PostgreSQL 实例，内存占用翻倍——这台机器上是真实约束
- 失效边界：当业务需要"跨订单和航班的复杂分析查询"时（比如运营报表），这个架构会很痛，需要单独引入数据仓库或 CDC

**📍 当前实现**
- 两个库各自跑在独立容器（`docker-compose.yml`，`flight-db:5433`、`booking-db:5434`），迁移在服务启动时自动执行
- **两个库对同一件事做了不同的类型选择**：`bookings.created_at` 是 `TIMESTAMPTZ`，而 `flights.departure_time`、`seat_reservations.created_at` 是 `TIMESTAMP`（无时区）。这不是有意的取舍，是分库之后缺少统一规范的结果——分库的隐性代价之一
- 两个库都没有配置 `max_connections`，用镜像默认值 100

**🔧 可以更好**
- **当需要"订单 + 航班"的联合查询时** → 在 `bookings` 里冗余航班号、起降时间等展示字段（写入时快照，和 `total_price` 同理）。**代价**：航班改期后订单里的信息会过期，需要明确"这是下单时的快照"而不是"当前状态"，否则会变成客服纠纷来源。
- **当内存成为瓶颈时** → 两个库合并到一个 PostgreSQL 实例的两个 database。**代价**：故障域合并，一个库的慢查询会影响另一个；且这是架构倒退，只应作为资源受限下的临时手段。

## 2.3 为什么内部用 gRPC

**S · 处境**
两个服务之间每天要通信几十万次，尖峰时每秒数千次。通信的内容是结构化的、字段固定的。

**T · 要求**
- 延迟预算紧（R2），序列化开销要小
- 契约要能被机器校验——字段拼错、类型写错应该在编译期发现，不是线上发现
- 错误要有**语义**，不只是一个数字——上游需要据此判断"能不能重试"

**A · 做法**
Protobuf 定义契约（`proto/flight/flight.proto`），`make proto` 生成两端代码，HTTP/2 长连接传输。

*为什么不是 REST/JSON*：JSON 序列化开销大、无类型校验、字段名靠字符串对齐。更关键的是**错误语义**：HTTP 状态码只有一层，而 gRPC 的 `codes` 是设计给 RPC 用的——`UNAVAILABLE`（服务不可达，可重试）和 `FAILED_PRECONDITION`（业务前提不满足，重试无意义）在 HTTP 里都会被塞进 5xx/4xx，上游没法据此做重试决策。第 7 章的重试分类**直接依赖这层语义**。

*为什么不是消息队列*：下单是**同步**操作——用户在等一个"成功还是失败"的答复，而且必须先知道座位扣成功了才能建订单。异步化意味着要么让用户轮询，要么改成"预订中"状态再回调，业务流程复杂度上一个台阶。**在 1.3 的尖峰场景下，队列削峰是正确答案**（见第 7 章），但那时队列削的是"进入系统的请求"，不是"服务间的调用"。

*为什么不是 GraphQL*：内部服务间调用的字段集合是固定的、由代码决定的，GraphQL 解决的"客户端自选字段"问题在这里不存在。

**R · 代价与边界**
- 调试成本上升：不能用 `curl` 直接打，要 `grpcurl` 或写客户端
- 契约变更要走生成流程，改 proto 后必须 `make proto`，忘了就是编译错误（这其实是好事）
- 浏览器不能直接调用 gRPC，所以对外必须有一层 REST 转换——这直接导出了 2.4 的决定
- 失效边界：服务数量增多后，点对点 gRPC 的连接数是 O(n²)，且每对连接的超时、重试、熔断都要各自配置

**📍 当前实现**
- 4 个 RPC：`SearchFlights` / `GetFlight` / `ReserveSeats` / `ReleaseReservation`
- **传输是明文的**（`booking-service/internal/grpcclient/flight.go:37` 用 `insecure.NewCredentials()`），认证靠 `x-api-key` metadata（D-08）
- **整条调用链上没有任何一处设置超时**——`grpcclient` 里没有一个 `context.WithTimeout`，用的是 Echo 传下来的 request context（无 deadline）。后果见下方 🔧

**🔧 可以更好**
- **立刻**（这是 R4 的硬要求，当前不满足）→ 给每个 gRPC 调用加 `context.WithTimeout`。当前 `retryableCodes` 里写着 `codes.DeadlineExceeded: true`（`grpcclient/flight.go:26`），但**这个分支永远不会被触发**，因为没人设过 deadline。下游卡住时 booking-service 会一直等，熔断器也记不到失败（调用根本没返回），HTTP 连接持续堆积直到耗尽。**代价**：超时值设短了会在尖峰锁等待时误杀正常请求（第 5 章会算出锁等待的量级），设长了等于没设——这个值必须由压测出来的 p99 决定，不能拍脑袋。已登记：[D-25](../tasks/D-25-no-timeouts-anywhere.md)，它同时是 [D-21](../tasks/D-21-half-open-no-probe-limit.md) 的前置。
- **当服务数超过 4~5 个时** → 引入服务网格或统一的调用框架，把超时/重试/熔断从业务代码里抽走。**代价**：多一层 sidecar，延迟增加、内存增加、排障多一跳；在两个服务的规模下纯属负担。

## 2.4 为什么外部只有一个入口

**S · 处境**
外部客户端（浏览器、App）需要搜航班、查航班、下单、查订单、取消。这些能力分属两个服务。

**T · 要求**
- 库存的所有权方不能被外部直接触达——否则 2.1 的边界就漏了
- 客户端不应该知道后端拆了几个服务

**A · 做法**
`booking-service` 是唯一的公开入口（:8080），它自己暴露 `/flights` 和 `/flights/{id}` 两个**纯转发**端点，把请求翻译成 gRPC 交给 flight-service。flight-service 只开 gRPC :50051 和一个仅供 `/metrics` 的 HTTP :9091。

*为什么不是各自暴露 REST*：那样 flight-service 就有了对外的攻击面和对外的契约，`ReserveSeats` 一旦能被外部直接调用，"库存唯一仲裁者"这个前提就崩了——任何人都可以绕开订单直接扣座位。

*为什么不是独立的 API Gateway*：网关是正确的长期方向（统一认证、限流、日志、路由），但在两个服务的规模下，多一个容器、多一跳延迟、多一处配置，收益为负。**当前的做法本质上是"把网关的职责临时寄放在 booking-service 里"**——这是个自觉的临时方案，不是终局。

*为什么不是 BFF*：客户端只有一种，没有多端差异要抹平。

**R · 代价与边界**
- **booking-service 承担了两个身份**：订单的业务所有者 + 航班查询的代理。这两个身份的负载特征完全不同（查询可缓存、量大；下单不可缓存、量小），混在一个进程里意味着**它们无法分别扩容，且互相争抢同一个 Go 运行时和同一个连接池**
- 尖峰时这个问题会放大：2000 QPS 的查询和下单挤在同一个进程，查询的 goroutine 调度延迟会直接抬高下单的延迟
- 失效边界：当读流量和写流量需要分别扩容时，这个决定就到头了——那时要么拆出独立的查询服务，要么上真正的网关

**📍 当前实现**
- 路由由 OpenAPI 规范生成（`booking-service/api/openapi.yaml` → `api.gen.go`），6 个端点
- `/flights` 和 `/flights/{id}` 是纯转发，不碰 `booking_db`
- **没有任何限流、没有任何认证**——外部入口是完全开放的。在 1.3 的尖峰场景下，2000 QPS 会毫无阻拦地全部进入系统，一直打到数据库的行锁上

**🔧 可以更好**
- **当尖峰场景需要保护后端时** → 在入口加限流（令牌桶），并对"同一航班的下单"单独限流。**代价**：限流阈值设定需要知道后端真实容量，而这个数当前不存在（见第 1 章 📍）；且限流会把"排队等待"变成"直接拒绝"，用户体验从"慢"变成"抢不到"，这是产品决策不是技术决策。
- **当需要区分用户时** → 入口加认证，`user_id` 从 token 取而不是从请求体取。**代价**：当前 `POST /bookings` 的 `user_id` 由客户端自由填写，任何人都能替别人下单——加认证会改变 API 契约，所有客户端都要改。

# 第 3 章：需要哪些 API

第 2 章定了"外部只有一个入口、内部用 gRPC"。本章定这个入口具体提供什么、每个端点为什么存在、以及**失败时说什么话**。

最后一点最容易被轻视，但它是整个系统对外的**唯一诚实度来源**：一个 API 如果把"座位卖完了"和"数据库炸了"都返回 500，那么客户端和监控系统都无法区分正常业务拒绝和真实故障——第 8 章的错误率 SLI 会直接被污染。

## 3.1 契约优先：先写规范，再生成代码

**S · 处境**
两套接口要维护：对外 REST（浏览器/App 调用）和对内 gRPC（两个服务之间）。接口一旦上线就有人依赖，改错了是线上事故。

**T · 要求**
- 接口定义要**唯一权威**——不能出现"文档说有这个字段，代码里没有"
- 字段名拼错、类型写错要在**编译期**暴露，而不是线上

**A · 做法**
两边都是契约优先，源文件是唯一真相：

| 契约 | 源文件 | 生成物 | 生成命令 |
|---|---|---|---|
| REST | `booking-service/api/openapi.yaml` | `api.gen.go` | `make proto` |
| gRPC | `proto/flight/flight.proto` | `flight-service/pb/flight/*.pb.go` | `make proto` |

生成的代码里有一行是这套机制的关键（`booking-service/internal/handler/booking.go:38`）：

```go
var _ api.ServerInterface = (*BookingHandler)(nil)
```

这行的作用是**编译期断言**：如果 `openapi.yaml` 里加了一个端点而 handler 没实现，或者参数类型对不上，`go build` 直接失败。**契约的一致性不靠人记住，靠编译器。**

*为什么不是手写路由再补文档*：文档和代码会漂移，而且漂移无人察觉。这个仓库里已经有一个现成的例子——根 `README.md` 曾写"12 个容器"而实际是 13（`docs/architecture/overview.md:61` 记了这次漂移）。**能生成的东西就不要手写，能校验的漂移就不要靠自觉。**

*为什么不是共用一套契约*（比如 gRPC-Gateway 从 proto 生成 REST）：能少维护一份文件，但会让对外契约被对内契约绑架——内部 RPC 的字段命名、错误码、粒度都是给程序看的，直接暴露给外部客户端会很别扭。**对外契约和对内契约的变更频率与受众都不同，应该分开演进**（这和 CLAUDE.md 第 3 节按"更新触发"分层是同一个道理）。

**R · 代价与边界**
- 改接口要走"改规范 → `make proto` → 改实现"三步，比直接改代码慢
- 生成物必须进 Git（否则新克隆的仓库编译不过），于是每次生成都会产生大量 diff 噪声
- **生成的是接口，不是校验**——见下方 📍
- 失效边界：当有多个客户端、多个版本需要同时支持时，单个 `openapi.yaml` 不够，需要版本化的契约管理

**📍 当前实现**
- `make proto` 一条命令生成两套代码；CLAUDE.md 明令禁止手改 `*.pb.go` 和 `api.gen.go`
- **规范里的校验约束没有生效**：`openapi.yaml:299` 给 `seat_count` 写了 `minimum: 1`，字段声明了 `format: uuid`，但 `booking-service/cmd/main.go` 里**没有注册 OpenAPI 请求校验中间件**（只有 RequestID / requestLogger / Recover / metrics 四个）。所以这些约束是文档，不是行为
- 实际生效的校验是 handler 里手写的一行 `if req.SeatCount < 1`（`handler/booking.go:95`）。**规范和实现在这里已经分家了**——规范说"最小 1"，实现也说"最小 1"，但它们是两处独立的事实，改了一处另一处不会跟着变
- 已登记：[D-18](../tasks/D-18-openapi-request-validation.md)

**🔧 可以更好**
- **当输入校验规则超过两三条时** → 注册 `oapi-codegen` 的请求校验中间件，让 `openapi.yaml` 里的约束真正生效，删掉 handler 里的手写校验。**代价**：(a) 校验失败的错误信息由中间件生成，格式不受控，可能和现有的 `api.Error` 结构不一致；(b) 校验发生在 handler 之前，日志和指标里看到的会是中间件的响应而不是业务响应，排障时要知道这一层的存在。

## 3.2 为什么是这 6 个端点

**S · 处境**
1.1 里的旅客旅程是：搜航班 → 看详情 → 下单 → 查订单 → 取消。

**T · 要求**
- 覆盖完整旅程，不多不少
- 端点粒度要匹配前端的一次交互，避免前端为一个页面调五次

**A · 做法**

| 端点 | 存在理由 | 打到哪 |
|---|---|---|
| `GET /flights?origin&destination&date` | 旅程第一步，列表页 | gRPC `SearchFlights` |
| `GET /flights/{id}` | 详情页，也是下单前确认价格的地方 | gRPC `GetFlight` |
| `POST /bookings` | 唯一的写入口，也是唯一争抢库存的操作 | gRPC `GetFlight` + `ReserveSeats` + 本地 INSERT |
| `GET /bookings?user_id` | "我的订单"列表 | 只查 `booking_db` |
| `GET /bookings/{id}` | 单个订单详情 | 只查 `booking_db` |
| `POST /bookings/{id}/cancel` | 取消 | gRPC `ReleaseReservation` + 本地 UPDATE |

*为什么取消是 `POST /{id}/cancel` 而不是 `DELETE /bookings/{id}`*：因为**取消不是删除**。订单取消后必须留档——用户要能看到取消记录，运营要能查历史，将来还可能要退款。`DELETE` 的语义暗示资源消失，会误导客户端。而且取消是一个**状态迁移**（`CONFIRMED → CANCELLED`），迁移是有业务规则的（已取消的不能再取消，`service/booking.go:211`），把它表达成一个动作端点比表达成资源删除更诚实。

*为什么没有 `PUT /bookings/{id}`*（改签、改人数）：改人数意味着要在同一个事务里增减库存，是 `ReserveSeats` 和 `ReleaseReservation` 的组合，跨库一致性问题会翻倍。当前范围裁掉了它。

*为什么没有航班管理端点*：见 1.1，有意裁剪。

*为什么读航班要经过 booking-service 转发而不是直连*：见 2.4。

**R · 代价与边界**
- `GET /bookings?user_id=X` 的 `user_id` 由客户端自由填写，**任何人都能查任何人的订单**——没有认证就没有授权，见 2.4 🔧
- 没有分页。`ListBookings` 返回该用户的全部订单，订单多了会是个大响应
- 失效边界：端点数量增长后，这种"一个端点一个 handler 方法"的结构还能撑，但跨端点的公共逻辑（认证、限流、审计）会开始重复，那时需要中间件层次化

**📍 当前实现**
- 6 个端点全部实现，路由由 `api.RegisterHandlers(e, h)` 注册（`booking-service/cmd/main.go:104`）
- `ListBookings` 无分页、无排序
- `POST /bookings` 的 `user_id` 来自请求体，不来自任何凭证

**🔧 可以更好**
- **当单个用户订单数可能超过几十条时** → `GET /bookings` 加游标分页。**代价**：API 契约变更；且游标分页要求有稳定排序键，`created_at` 可能重复，需要 `(created_at, id)` 复合游标。

## 3.3 错误语义：失败的时候说什么话

**S · 处境**
下单会以很多种方式失败：航班不存在、座位不够、下游挂了、熔断打开、数据库炸了。客户端和监控系统都需要**区分**它们。

**T · 要求**
- 客户端要能据此决定**下一步做什么**：改参数重试？稍后重试？放弃？
- 监控要能据此区分**正常业务拒绝**和**真实故障**——否则错误率 SLI 会被"座位卖完了"污染（这是 R3 里特意写"不含正常业务拒绝"的原因）

**A · 做法**
两次映射：flight-service 把内部错误映射成 gRPC code，booking-service 把 gRPC code 映射成 HTTP 状态码。

| 业务场景 | 内部错误 | gRPC code | HTTP | 客户端该怎么办 |
|---|---|---|---|---|
| 航班不存在 | `ErrNotFound` | `NOT_FOUND` | **404** | 放弃，参数错了 |
| 座位不足 | `ErrInsufficientSeats` | `RESOURCE_EXHAUSTED` | **409** | 放弃或改人数——**这是正常业务结果，不是故障** |
| 订单已取消 | `ErrAlreadyCancelled` | — | **409** | 放弃 |
| 熔断器打开 | `ErrCircuitOpen` | — | **503** | 稍后重试 |
| 请求体非法 | — | — | **400** | 改参数 |

关键的一条是**座位不足 → 409 而不是 400 或 500**：

- 不是 400，因为请求本身完全合法——同样的请求在一分钟前会成功
- 不是 500，因为系统运转完全正常——**没有任何人需要被叫醒**
- 409 Conflict 的语义正是"请求与资源的当前状态冲突"，而"座位卖完了"就是资源状态

这个区分在 1.3 的尖峰场景下至关重要：3 万人抢 300 座，**注定有 2.97 万个请求要失败**。如果它们返回 500，错误率会瞬间飙到 99%，告警全响，而系统其实工作得完美无缺。

*为什么不用 `FAILED_PRECONDITION` 表示座位不足*：`RESOURCE_EXHAUSTED` 的语义更贴——它就是"资源用尽"。而且 `FAILED_PRECONDITION` 在 gRPC 规范里暗示"客户端应该先做点别的再重试"，座位不足没有这样的"别的"可做。

**R · 代价与边界**
- 两次映射意味着两处要保持一致，加一个新错误要改两个地方
- 映射表本身没有测试覆盖它的完整性——漏映射一个 code 不会有任何提示，只会静默落到默认分支

**📍 当前实现**

映射表里**只有前五行是实现了的**，剩下的 gRPC code 全部落到 `err != nil` 的默认分支 → **HTTP 500**：

| gRPC code | 当前 HTTP | 应该是 | 问题 |
|---|---|---|---|
| `UNAVAILABLE`（下游不可达） | **500** | 503 | 500 暗示"服务器有 bug"，客户端不会重试；503 才是"稍后再来" |
| `DEADLINE_EXCEEDED` | **500** | 504 | 同上 |
| `UNAUTHENTICATED`（API key 错） | **500** | 500 或 502 | 配置错误被伪装成服务器 bug，排障时会找错方向 |
| `INVALID_ARGUMENT` | **500** | 400 | 客户端的错被算成服务端的错，**直接污染错误率 SLI** |

代码位置：`handler/booking.go:122-128`（以及 `:53-59`、`:78-84`、`:184-190` 同构）。

还有一处更直接的问题：**`err.Error()` 被原样返回给外部客户端**（`handler/booking.go:58, 83, 127, 148, 160, 189`）：

```go
return c.JSON(http.StatusInternalServerError, api.Error{Message: err.Error()})
```

这个字符串里可能包含 SQL 错误详情、gRPC 内部消息、连接目标地址（含内部容器 IP 和端口）。**内部实现细节直接泄漏到公网**。

两个问题已分别登记：[D-19](../tasks/D-19-grpc-http-status-mapping.md)（映射不完整）、[D-20](../tasks/D-20-internal-error-disclosure.md)（错误详情外泄）。它们在同一段代码里，但一条影响 SLI 正确性、一条是信息泄漏，验收标准不同。

**🔧 可以更好**
- **上线前**（这条同时是安全问题和 SLI 污染问题）→ 补全 gRPC code → HTTP 的映射表，并把 500 响应体的 `Message` 换成固定文案 + 一个 `request_id`，真实错误只进日志。**代价**：(a) 客户端排障时看不到细节了，需要用 request_id 去问后端——这要求日志里的 request_id 确实能查到（当前 `middleware.RequestID()` 只在 booking-service 边界生成，**没有透传到 gRPC**，所以跨服务查不通，见 D-11）；(b) 映射表变长后需要测试保证完整性。
- **当映射规则稳定后** → 把映射抽成一张表驱动的函数并加表格测试，而不是四处重复的 `if errors.Is(...)`。**代价**：表驱动会让"某个端点想对某个错误特殊处理"变麻烦，需要留出覆盖机制。

# 第 4 章：数据模型

> 本章讲**静态结构**：三张表为什么存在、每个字段为什么存在、每条约束防什么。
>
> 这些结构在并发下**如何被使用**，见第 5 章——有几个字段（尤其 `booking_id`、`available_seats`）的存在理由其实在那一章，本章会指过去。

## 4.0 三张表的分工

```
flight_db                                    booking_db
┌──────────────────┐   ┌───────────────────┐   ┌──────────────────┐
│ flights          │◄──┤ seat_reservations │╌╌╌┤ bookings         │
│ 航班的静态信息    │FK │ 库存的变动凭证     │逻辑│ 订单：谁买的      │
│ + 当前余位        │   │ 一次预留一条       │引用│ 花了多少钱        │
└──────────────────┘   └───────────────────┘   └──────────────────┘
     ▲ 会被并发修改          ▲ 只增不改（除状态）      ▲ 与库存无关
```

一句话概括：**`flights` 是"现在还剩多少"，`seat_reservations` 是"这些座位是怎么少的"，`bookings` 是"谁买走的"。**

## 4.1 为什么 seat_reservations 要独立存在

这是本章最值得想清楚的一个问题。表面上看，它的每一条记录都对应一个订单，字段还比 `bookings` 少——**看起来就是订单的影子表**。

**S · 处境**
库存变动需要一个凭证。而"变动"来自两个方向：下单减少、取消归还。

**T · 要求**
- gRPC 重试必须幂等——同一次预留重复执行不能重复扣减（第 5 章 5.2）
- 要能回答"这个航班的座位都去哪了"
- 库存的所有权在 flight-service，而订单在另一个库——**flight-service 不能依赖 `bookings` 表存在**

**A · 做法**
独立成表，一次预留一条记录，带自己的状态机（`ACTIVE` → `RELEASED` / `EXPIRED`）。

*为什么不是直接在 `flights` 上加减、不留记录*：那样 `available_seats` 就是一个**没有出处的数字**。它变了，你无法回答"是谁改的、什么时候、改了多少"。更致命的是——**幂等无处附着**：幂等需要一个"这次操作已经做过了"的持久标记，而 `UPDATE flights SET available_seats = available_seats - 1` 这条语句本身不留任何痕迹，重复执行就是重复扣减。**`seat_reservations` 的第一存在理由，是给幂等提供一个可以加唯一约束的地方**（见 5.2）。

*为什么不是复用 `bookings` 表*：`bookings` 在另一个库。flight-service 要查"这个 booking_id 是否已经预留过"，就必须跨库查询——这直接违反 2.2 的分库边界。**库存的凭证必须和库存在同一个库、同一个事务里**，否则幂等检查和扣减无法原子。

*为什么状态机是三态而不是两态（存在/删除）*：物理删除会丢失"这个订单曾经预留过又释放了"的事实，而这个事实在对账时是必需的——见 5.3 🔧 里的孤儿预留检测。**删除是不可逆的信息丢失，状态迁移不是。**

**R · 代价与边界**
- 多一张表、多一次 INSERT，写路径延迟增加（在持锁窗口内，直接影响 5.1 算出的单航班吞吐上限）
- `available_seats` 和 `seat_reservations` 必须保持一致，而这个一致性**只能由应用层的事务保证**——数据库只能用 `CHECK` 兜住范围，兜不住"数值是否正确"
- 表会持续增长且没有归档策略：20 万单/日意味着一年 7300 万行

**📍 当前实现**
- 表结构：`flight-service/migrations/001_init.up.sql`
- 状态实际只有两个在用：`ACTIVE`（`repository/flight.go:124`）和 `RELEASED`（`:163`），`EXPIRED` 无生产者（见 5.4 问题 3）
- 没有归档、没有分区、没有清理任务

**🔧 可以更好**
- **当表行数影响索引性能时**（经验值：单表过亿行）→ 按 `created_at` 做时间分区，历史分区归档。**代价**：分区表的唯一约束必须包含分区键，而 `booking_id UNIQUE` 是全局唯一约束——**分区会直接破坏 5.2 的幂等保证**，除非改成 `(created_at, booking_id)` 复合唯一，那样幂等语义就变了。**这是一个分区与幂等直接冲突的例子，不能简单套用"大表就分区"的经验。**

## 4.2 available_seats 为什么物化成一列

**S · 处境**
"这个航班还剩几个座位"这个数，理论上可以从 `total_seats - SUM(活跃预留的座位数)` 算出来。

**T · 要求**
- 尖峰时每秒数千次查询和修改这个数（R2）
- R1：并发修改必须互斥

**A · 做法**
物化成 `flights.available_seats` 一列，每次预留/释放时增减。

*为什么不用聚合查询实时算*：两个理由，第二个是决定性的。

1. 性能：每次下单都要 `SUM` 一遍该航班的全部预留记录，随着记录增长而变慢
2. **决定性理由——聚合查询无法加锁。** 5.1 的整个并发控制建立在"锁住代表这个航班库存的那一行"上。而 `SUM(...)` 锁不住任何东西：它是对一组行的计算，你无法对"这个航班的库存"这个逻辑资源取得互斥。**物化成一列，本质上是为了给这个逻辑资源找一个物理载体，好让 `FOR UPDATE` 有东西可锁。**

*为什么这不违反 3NF*：它确实是可推导的冗余，属于**有意的反规范化**。规范化的目标是消除更新异常，而这里用"所有修改都在同一个事务里"来保证不出现异常——用一致性责任换取可锁定性和性能。

**R · 代价与边界**
- 这一列必须和 `seat_reservations` 保持一致，责任完全在应用层
- 数据库只能用 `CHECK` 兜住范围（`>= 0`、`<= total_seats`），兜不住"数值是否正确"——**5.4 的重复归还缺陷正是这个边界的实证：多加了座位，`CHECK` 完全没意见**
- 它成了全系统最热的一个字段，也是 5.1 算出的吞吐上限的所在地

**📍 当前实现**
- `available_seats INT NOT NULL CHECK (available_seats >= 0)` + `CONSTRAINT chk_available_le_total CHECK (available_seats <= total_seats)`
- 增减位置只有两处：`repository/flight.go:114-117`（减）、`:154-157`（加）
- **没有任何机制校验它和 `seat_reservations` 是否真的一致**

**🔧 可以更好**
- **当怀疑库存数值漂移时**（5.4 的缺陷会导致这个）→ 加一个对账查询：`SELECT f.id, f.total_seats - f.available_seats AS deducted, COALESCE(SUM(r.seat_count),0) AS reserved FROM flights f LEFT JOIN seat_reservations r ON r.flight_id=f.id AND r.status='ACTIVE' GROUP BY f.id HAVING ...`，找出两者不等的航班。**代价**：这是全表扫描 + 聚合，不能在高峰跑；且它只能发现漂移、不能判断哪一边是对的——修复需要人工介入。

## 4.3 total_price 为什么是快照

**S · 处境**
订单金额 = 座位数 × 单价。单价存在 `flights.price` 里，而航班会改价。

**T · 要求**
- 已成交订单的金额**不能**随航班改价而变化

**A · 做法**
下单时把 `seat_count × price` 算出来存进 `bookings.total_price`（`service/booking.go:150`）。

*为什么这不是冗余*：函数依赖的左边是**订单**，不是"航班的当前价格"。"这个订单值多少钱"是订单自身的属性，只是它的初始值来自航班当时的价格。**不存它，改价后所有历史订单的金额会集体变化——这是财务事故，不是数据优化。**

同理适用于任何"成交时快照"的场景：汇率、税率、优惠券折扣。

**R · 代价与边界**
- 无法从订单反推"当时的单价"（只有总价和座位数，能除出来，但如果将来有折扣就除不出来了）
- 快照的准确性完全取决于**快照那一刻读到的价格是否正确**——见下方 📍

**📍 当前实现**
- `total_price BIGINT NOT NULL CHECK (total_price > 0)`
- **快照读的是缓存里的价格，不是数据库当前价格**：`totalPrice` 用的是 `GetFlight` 的返回值，而 `GetFlight` 走 Redis，TTL 5 分钟（`cache/redis.go:14`）。改价后 5 分钟内的订单会按旧价成交
- 当前没有改价路径（见 1.1），所以触发不了。已登记：[D-26](../tasks/D-26-price-snapshot-from-cache.md)，详见 5.3 📍 和 🔧

## 4.4 状态为什么是 VARCHAR + CHECK

三张表的 `status` 都是 `VARCHAR(20) + CHECK (status IN (...))`，不是 PostgreSQL 的 `ENUM` 类型。

*为什么不用 `ENUM`*：`ENUM` 的增删值需要 `ALTER TYPE`，在旧版本 PostgreSQL 里不能在事务中执行、也不能删除值，迁移会很别扭。而 `CHECK` 约束的修改就是普通的 `ALTER TABLE ... DROP/ADD CONSTRAINT`，可以在一个迁移里干净地完成。

*为什么不用 `SMALLINT` 存数字码*：省几个字节，但代价是**每次看数据库都要查映射表**。`SELECT * FROM bookings` 时看到 `CANCELLED` 和看到 `2`，排障效率差很多。**为运维可读性付这几个字节是划算的**——这也是本文档的立场：这个系统的首要用户是要运维它的人。

*为什么要有 `CHECK` 而不是只靠应用层*：和 4.2 的 `CHECK` 同理，防的是应用层写错时**静默产生脏数据**。没有 `CHECK`，一个拼写错误的 `"CANCELED"`（少个 L）会被数据库愉快接受，然后所有按状态过滤的查询都会漏掉它，而且不报任何错。

**📍 当前实现**：三张表的状态枚举分别是——`flights`: SCHEDULED / DEPARTED / CANCELLED / COMPLETED（**只有 SCHEDULED 会出现**，没有代码写其他值）；`seat_reservations`: ACTIVE / RELEASED / EXPIRED（EXPIRED 无生产者）；`bookings`: CONFIRMED / CANCELLED（两个都在用）。**九个状态值里只有四个被实际写入过。**

# 第 5 章：并发与一致性

> 第 4 章讲了每张表、每个字段"是什么、为什么存在"。本章讲这些结构**在并发下如何被使用**，以及它们合起来保证了什么、保证不了什么。
>
> 这是全文密度最高的一章，因为 R1（超卖=0）这条硬要求的全部实现都在这里。

## 5.0 先把问题说清楚

尖峰时刻，3 万人抢同一个航班的 300 个座位。翻译成技术语言：

**每秒数千个事务，要读同一行数据、判断、然后修改它。** 而且判断和修改之间不能被别人插队——否则两个请求同时读到"还剩 1 个座位"，然后都扣减，就超卖了。

这是并发控制的教科书问题。区别在于**这里不允许"偶尔出错"**：超卖不是数据不一致，是要赔钱的业务事故。

## 5.1 用悲观锁保护库存扣减

**S · 处境**
`flights` 表里代表这个航班的**那一行**，成为全系统争抢最激烈的资源。尖峰 60 秒内，它要承受每秒数千次"读-判断-写"。

**T · 要求**
- **R1：超卖 = 0**（硬）
- R2：p95 < 500ms（软）
- 库存扣减和预留记录的创建必须**同生同死**——不能出现"扣了座位但没有预留记录"

**A · 做法**
单个数据库事务内，四步：

```sql
BEGIN;
  -- 1. 幂等前置检查（repository/flight.go:86-92）
  SELECT ... FROM seat_reservations WHERE booking_id = $1 AND status = 'ACTIVE';
  -- 命中则直接返回，不重复扣减

  -- 2. 悲观锁锁住航班行（:99-101）—— 持锁窗口从这里开始
  SELECT available_seats FROM flights WHERE id = $1 FOR UPDATE;

  -- 3. 判断 + 扣减（:109-118）
  --    available < seatCount → ErrInsufficientSeats，事务回滚
  UPDATE flights SET available_seats = available_seats - $1 WHERE id = $2;

  -- 4. 写预留记录（:121-126）
  INSERT INTO seat_reservations (flight_id, booking_id, seat_count, status) VALUES (..., 'ACTIVE');
COMMIT;  -- 持锁窗口到这里结束
```

`FOR UPDATE` 让第 2 步取得该行的**排他锁**。同一航班的其他事务执行到第 2 步时全部阻塞排队，直到本事务 `COMMIT` 或 `ROLLBACK`。于是"读-判断-写"这个复合操作对同一航班而言是**严格串行**的。

三层防护，从上到下：

| 层 | 机制 | 挡什么 |
|---|---|---|
| 应用层 | `FOR UPDATE` 串行化 | 并发竞争导致的超卖 |
| 事务层 | 四步同一事务，失败全回滚 | 扣了座位但没有预留记录 |
| 数据库层 | `CHECK (available_seats >= 0)` | **应用层逻辑写错时的兜底** |

第三层的意义要说清楚：它不是冗余。前两层依赖代码正确，第三层不依赖任何代码——即使有人写了个新的 UPDATE 语句忘了加锁，数据库也不会接受负库存。**它保证的是"错误会以事务失败的形式暴露出来"，而不是"悄悄写进一个错误的数字"。** 这两者的排障成本差好几个数量级。

*为什么不是乐观锁*（`version` 字段 + CAS 重试）：乐观锁的适用前提是**冲突罕见**。这里的场景恰恰相反——3 万人抢 300 座，绝大多数请求都会撞车。乐观锁在高冲突下会退化：每次冲突都要重试，重试又制造新的冲突，最终变成活锁，吞吐比悲观锁**更低**，而且延迟分布极不稳定（有的请求重试 1 次，有的重试 20 次）。**悲观锁在高冲突下更快，这一点反直觉但很重要。**

*为什么不是 `SERIALIZABLE` 隔离级别*：让数据库自动检测冲突并中止事务。但 PostgreSQL 的 SERIALIZABLE 用的是 SSI（可串行化快照隔离），冲突时抛 `40001` 序列化失败，**应用必须自己重试**——本质上又回到了乐观锁的问题，而且失败时机更不可控。此外它对全库所有事务生效，开销加在不需要它的读路径上。

*为什么不是 Redis 原子扣减*（`DECRBY` / Lua 脚本）：这是尖峰场景的正确方向，但代价必须看清——Redis 不落盘则宕机丢库存，落盘（AOF `always`）则失去了性能优势；而且库存的真相分裂成两处（Redis 和 PostgreSQL），需要额外的对账机制。**这个代价只有在悲观锁真的撞到上限时才值得付**，见下方 🔧。

*为什么不是在应用层加互斥锁*：多实例部署时进程内的锁完全无效，必须是分布式锁——而分布式锁的正确实现（续租、防误删、脑裂）比数据库行锁难得多，且它自己就是个新的单点。**数据库行锁的最大优点是：它和数据在同一个地方，不存在"锁活着但数据没了"的状态。**

**R · 代价与边界**

这是全文最重要的一段推导：

```
单航班吞吐上限 = 1 ÷ 持锁窗口时长
持锁窗口 = SELECT FOR UPDATE 到 COMMIT 之间的全部时间
         = 一次 UPDATE + 一次 INSERT + 一次 commit fsync
         ≈ 1–3 ms（本机 WSL2 + Docker 卷）
∴ 单航班上限 ≈ 300–1000 单/s
```

**这个数字加机器、加服务实例、加连接池全都不会变**——它是一条串行队列，队列的速度只取决于每个事务持锁多久。这一点必须刻在脑子里：**遇到"下单变慢"时，加机器是没用的。**

对照 1.3 的尖峰目标 2000 QPS 打单航班：**必然撞穿**。撞穿之后的表现是级联的：

1. 请求在数据库侧排队等锁 → `ReserveSeats` 延迟上升
2. 上游没有超时（见 2.3 📍）→ booking-service 的 goroutine 和连接堆积
3. `pgxpool` 连接被耗尽 → 连查订单这种无关请求也开始等连接
4. 熔断器记不到失败（调用未返回）→ 保护机制失效
5. 最终整个 booking-service 无响应

**注意第 2、3、4 步：真正把系统拖垮的不是锁本身，是"没有超时"。** 有超时的话，撞上限的表现是"一部分用户下单失败"（可接受）；没有超时的表现是"整个服务挂掉"（不可接受）。这是 2.3 里那条 🔧 是硬要求的原因。

另一个边界：**持锁期间不能做任何慢操作**。当前事务里只有本地 SQL，这是对的。如果哪天有人在这个事务里加了一次 RPC 调用或一次 HTTP 请求，持锁窗口会从毫秒变成百毫秒，单航班上限直接掉一到两个数量级。

**📍 当前实现**
- 逻辑完整且正确：`flight-service/internal/repository/flight.go:81-131`
- **`pgxpool` 未配置任何参数**（`repository/postgres.go:42` 直接 `pgxpool.New(ctx, dsn)`），MaxConns 取默认值 `max(4, NumCPU)` = 本机 12。这意味着**flight-service 最多只有 12 个并发事务**，锁的真实上限根本压不到——瓶颈会先出现在连接排队上
- 两个 PostgreSQL 都用镜像默认 `max_connections = 100`
- 事务隔离级别是 PostgreSQL 默认的 **READ COMMITTED**，没有显式设置——这个选择是对的（`FOR UPDATE` 在 READ COMMITTED 下已经足够），但它是默认值而非有意选择，值得知道

**🔧 可以更好**
- **当压测显示"连接排队时间 > 锁等待时间"时** → 显式配置 `pgxpool` 的 `MaxConns`（经验起点：CPU 核数 × 2 + 有效磁盘数），并提升为环境变量。**代价**：连接数越高 PG 侧内存开销越大（每连接约 5–10MB），这台机器只有 7.7 GiB 且要装 13 个容器，两个库的连接数之和必须留余量；且连接开太多会让锁竞争更激烈，延迟分布更差。相关：D-10。
- **当单航班下单速率持续超过约 500/s、且 `ReserveSeats` 的 p99 因锁等待超过 200ms 时** → 把库存预扣挪到 Redis（Lua 脚本保证原子性），PostgreSQL 只负责异步落库和最终对账。**代价**：(a) 库存真相分裂成两处，Redis 宕机会丢预扣状态，必须有对账任务；(b) 数据库的 `CHECK` 兜底失效——Redis 里没有 CHECK 约束，超卖的最后一道防线消失；(c) 系统从"强一致"变成"最终一致"，业务上要接受"极小概率超卖后人工处理"。**这是把 R1 从硬要求降级成软要求，是业务决策不是技术决策。**
- **当尖峰形状是"瞬时脉冲"而非"持续高压"时** → 入口加队列削峰（请求先入队、返回"处理中"、异步通知结果），而不是改造扣减逻辑。**代价**：下单从同步变异步，客户端要轮询或接收推送，产品流程要改；但库存逻辑一行都不用动，强一致性完整保留。**在 1.3 的场景（60 秒脉冲）下这个方案比 Redis 预扣更合适**，因为脉冲的总量（3 万人）远小于持续负载。

## 5.2 幂等：booking_id 唯一约束

**S · 处境**
第 7 章会讲，`ReserveSeats` 在遇到 `UNAVAILABLE` / `DEADLINE_EXCEEDED` 时会自动重试最多 3 次。但网络超时有个根本性的模糊：**上游收不到响应，无法区分"下游没执行"和"下游执行了但响应丢了"**。

**T · 要求**
- 同一个逻辑操作重复执行，**结果必须和执行一次相同**（硬）
- 这是重试机制能安全存在的**前提**——没有幂等就不能重试，重试会重复扣库存

**A · 做法**
`seat_reservations.booking_id` 上加 `UNIQUE` 约束，`booking_id` 由 booking-service 在调用前生成（`service/booking.go:120`）并作为幂等键传下去。

两层保护：

1. **事务开头的前置检查**（`repository/flight.go:86-92`）：查同 `booking_id` 的 ACTIVE 预留，命中直接返回，不进入扣减
2. **唯一约束兜底**：万一两个并发请求都通过了前置检查，其中一个的 `INSERT` 会违反唯一约束 → 整个事务回滚 → **连同它的扣减一起回滚**

第 2 层为什么必然正确，值得走一遍：两个同 `booking_id` 的请求并发到达，都在第 1 步没查到 ACTIVE 记录（`FOR UPDATE` 还没生效）。然后它们在第 2 步的航班行锁上排队——**串行化在这里发生**。先到的完成扣减和插入并提交；后到的拿到锁、扣减、然后 `INSERT` 撞上唯一约束、报错、整个事务回滚，扣减也一起没了。**最终结果：只扣了一次。**

这就是"约束 + 事务"的组合威力：**唯一约束把并发问题转成了事务失败，而事务失败是自动可回滚的。**

*为什么幂等键是 `booking_id` 而不是随机的 request_id*：因为业务语义就是"一个订单对应且只对应一次预留"。用 `booking_id` 让幂等性和业务不变量重合，不需要额外的表和过期清理。

*为什么不是让 flight-service 生成 ID 返回*：那样上游就没有幂等键可用了——重试时上游不知道该带什么标识，下游也认不出这是同一个操作。**幂等键必须由调用方生成，这是幂等设计的通用规则。**

**R · 代价与边界**
- 幂等的作用域是 **`booking_id` 的生命周期**。`booking_id` 一旦变了，幂等就不成立
- 一个订单永远只能对应一次预留，无法表达"同一订单分两次加座位"这种业务
- **失效边界见下方 📍——当前实现里这个边界比想象中窄得多**

**📍 当前实现**
- 约束存在：`booking_id UUID NOT NULL UNIQUE`（`flight-service/migrations/001_init.up.sql`）
- **但 `bookingID` 是在 `CreateBooking` 内部每次新生成的**（`booking-service/internal/service/booking.go:120`：`bookingID := uuid.New().String()`）
- 后果：**幂等只对"一次 `CreateBooking` 调用内部的 gRPC 重试"有效，对"客户端重发 `POST /bookings`"完全无效。**
  客户端因为超时或网络问题重发一次请求，会走进一个全新的 `CreateBooking`，生成一个全新的 `booking_id`，然后**正常地再扣一次库存、再建一条订单**。数据库层面这完全合法——两个不同的 `booking_id`，唯一约束毫无意见。
- 也就是说：**HTTP 入口这一层是没有幂等保护的。** 在 1.3 的尖峰场景下，用户看到转圈就狂点提交按钮，这个洞会被反复踩中。
- 已登记：[D-24](../tasks/D-24-booking-idempotency-key.md)

**🔧 可以更好**
- **当客户端可能重发请求时（即：现在）** → `POST /bookings` 接受 `Idempotency-Key` 请求头，booking-service 用它作为 `bookings` 表的唯一键（或单独的幂等记录表），命中则直接返回已有订单。**代价**：(a) API 契约变更，客户端必须配合生成并保存 key；(b) 需要决定 key 的保留期和清理策略；(c) "同 key 但请求体不同"要怎么处理必须明确定义（通常是返回 409）。
- **当无法要求客户端配合时** → 退化方案：用 `(user_id, flight_id, seat_count)` 加短时间窗口做去重。**代价**：会误杀"同一个人真的想连着买两次同样的票"这种合法操作，是用正确性换便利性。

## 5.3 为什么先扣库存、后落订单

**S · 处境**
`CreateBooking` 要在两个库各写一次：flight_db 扣库存、booking_db 建订单。**没有分布式事务**，所以必然有个顺序，而任何一个顺序都可能在中间失败。

**T · 要求**
- 失败时，宁可"少一点"也不能"多一点"——绝不能出现"订单存在但没有座位"（那是超卖的另一种形式，违反 R1）

**A · 做法**
顺序固定为：`GetFlight`（拿价格）→ `ReserveSeats`（扣库存）→ `INSERT bookings`。见 `booking-service/internal/service/booking.go:100-171`。

*为什么不是反过来*：先建订单再扣库存，那么"订单建了、扣库存失败"会留下一条**无效订单**——用户看到"下单成功"但实际没有座位。这直接违反 R1。

两种失败的对比：

| 顺序 | 中途失败的后果 | 谁受损 |
|---|---|---|
| 先订单后库存 | 订单存在、座位没扣 → **超卖** | 旅客（到机场发现没座位）+ 航司（赔偿） |
| **先库存后订单** | 座位扣了、订单不存在 → **库存泄漏** | 航司（少卖了几个座位） |

**选后者，因为代价可比。** 库存泄漏损失的是收入，超卖损失的是信任和赔偿金。这是个典型的"选择哪种失败模式"的决定——**分布式系统里你无法消除失败，只能选择失败的形状。**

*为什么不是两阶段提交（2PC）*：2PC 需要事务协调者，协调者本身是单点，且在协调者宕机时参与者会长时间持锁（阻塞协议）。在一个只有两个服务的系统里引入 2PC，复杂度远超收益。

*为什么不是 Saga 补偿*（步骤 3 失败时显式调 `ReleaseReservation` 回滚）：这是**正确的改进方向**，但要看清它的极限——补偿调用本身也会失败（网络断了、flight-service 挂了）。Saga 把泄漏的概率降低了一个数量级，但没有消除它。真正消除需要"补偿 + 重试队列 + 兜底对账"三件套。相关：D-06。

**R · 代价与边界**
- **已知且未解决的一致性缺口**：`ReserveSeats` 成功但 `INSERT bookings` 失败（booking_db 挂了、连接池耗尽、进程被杀），座位被扣但订单不存在，这些座位**永远不会被释放**——没有任何机制会发现它们
- 泄漏的座位无法被自动识别：`seat_reservations` 里有一条 ACTIVE 记录，`bookings` 里没有对应订单，但**没有任何代码会去比对这两个库**
- 失效边界：泄漏概率正比于 booking_db 的故障率 × 下单量。20 万单/日的规模下，即使 0.1% 的失败率也意味着每天 200 个座位悄悄消失
- 详见 D-06

**📍 当前实现**
- 顺序如上，`ReserveSeats` 失败时直接返回、不建订单——这部分是对的
- **`INSERT bookings` 失败时没有任何补偿**：`service/booking.go:164-167` 只记一条 Error 日志然后返回错误，扣掉的座位就留在那里了
- 没有对账任务，没有孤儿预留的检测
- 另一个被顺序掩盖的问题：`totalPrice` 用的是 `GetFlight` 返回的价格（`service/booking.go:150`），而 `GetFlight` 走的是 **Redis 缓存，TTL 5 分钟**（`cache/redis.go:14`）。所以**价格快照拍的是缓存里的价格，不是数据库当前价格**——改价后 5 分钟内的订单会按旧价成交。当前没有改价路径（见第 1 章），所以这个问题触发不了，但它是真实存在的。已登记：[D-26](../tasks/D-26-price-snapshot-from-cache.md)。

**🔧 可以更好**
- **当泄漏率变得可观测、或者上线前** → 先加**检测**再加修复：一个定期任务比对 `seat_reservations`（ACTIVE）和 `bookings`，找出没有对应订单的预留。**代价**：跨库查询要么走两次查询在应用层比对（简单但慢），要么引入 CDC（复杂）；且比对有时间窗口问题——正在进行中的下单会被误判为孤儿，需要"创建时间超过 N 分钟"的宽限期。**先做检测的理由是：不知道泄漏率的情况下，无法判断修复方案值不值得。**
- **当检测显示泄漏率不可接受时** → Saga 补偿：`INSERT bookings` 失败后立刻调 `ReleaseReservation`。**代价**：补偿本身会失败，需要重试队列，且要处理"补偿重试期间进程重启"——这需要把待补偿的操作持久化（本地消息表），复杂度显著上升。相关：D-06。
- **当价格快照的准确性变重要时** → `ReserveSeats` 直接返回权威价格（它本来就在事务里读了 `flights` 行），booking-service 用这个价格而不是缓存里的。**代价**：gRPC 契约变更；但这个改动很小且顺带消除了缓存旧价的问题，性价比高。

## 5.4 取消路径：座位怎么还回来

**S · 处境**
用户取消订单，座位要还回池子。这条路径同样跨两个库。

**T · 要求**
- 归还的座位数必须准确——多还了就是凭空造出座位（同样违反 R1，只是方向相反）
- 重复取消不能重复归还

**A · 做法**
`CancelBooking`（`service/booking.go:199-235`）：查订单 → 检查是否已取消 → `ReleaseReservation`（gRPC）→ `UPDATE bookings SET status='CANCELLED'`。

flight-service 侧（`repository/flight.go:137-172`）单事务内：查 ACTIVE 预留 → `available_seats + seat_count` → 预留标记 `RELEASED`。

**R · 代价与边界**
- 和 5.3 一样跨两个库，同样没有分布式事务，同样存在中途失败
- 但方向相反：这里失败的后果是"订单没取消但座位还了"或"订单取消了但座位没还"

**📍 当前实现**

这条路径有三个问题，其中第一个是**新发现的并发缺陷**：

**问题 1：并发取消会重复归还座位**（[D-23](../tasks/D-23-concurrent-release-double-refund.md)）

`ReleaseReservation` 的第一步查预留时**没有加 `FOR UPDATE`**（`repository/flight.go:142-148`）：

```sql
SELECT ... FROM seat_reservations WHERE booking_id = $1 AND status = 'ACTIVE';  -- 无锁
UPDATE flights SET available_seats = available_seats + $1 WHERE id = $2;
UPDATE seat_reservations SET status = 'RELEASED' WHERE id = $1;
```

在 READ COMMITTED 下，两个并发的取消请求可以**都读到同一条 ACTIVE 记录**（无锁，不阻塞），然后**都执行 `+ seat_count`**（`UPDATE` 各自取行锁，但两次加法都会生效），最后都把同一条记录标成 RELEASED。

**结果：座位被归还了两次，库存凭空多出 N 个。**

`chk_available_le_total`（`available_seats <= total_seats`）能挡住"航班本来就满"的情况，但只要航班没坐满，多出来的座位就会**静默地写进数据库**。

对比 5.2 的 `ReserveSeats`：那里靠 `booking_id UNIQUE` 让第二个事务的 `INSERT` 失败并整体回滚。而释放路径**没有任何唯一约束保护**——它只做 `UPDATE`，`UPDATE` 不会因为"已经是 RELEASED 了"而报错。

上游的 `if b.Status == "CANCELLED"` 检查（`service/booking.go:211`）挡不住：那个检查读 `bookings` 时也没加锁，两个并发请求都会通过。

**问题 2：释放失败被静默吞掉**

`service/booking.go:218-223`——`ReleaseReservation` 失败时**只记一条 Error 日志，然后继续把订单标记为 CANCELLED**：

```go
_, err = s.flights.ReleaseReservation(ctx, b.ID)
if err != nil {
    s.log.Error("gRPC ReleaseReservation failed (best-effort)", ...)
}   // ← 没有 return，流程继续
```

结果：**订单显示已取消，用户以为退成功了，但座位从未还回池子**。这是 D-06 的镜像问题（那个是"扣了没建单"，这个是"取消了没还座位"），但**方向和成因都不同，未单独登记**。

注释里写的 `best-effort` 说明这是有意的选择——优先保证"用户能取消掉订单"。这个选择本身可以辩护，但它必须被记录和监控，而当前它只是一行日志。

**问题 3：`EXPIRED` 状态没有生产者**

`seat_reservations.status` 的 `CHECK` 允许 `'EXPIRED'`，proto 定义了 `RESERVATION_STATUS_EXPIRED`，handler 里有映射（`flight-service/internal/handler/flight.go:140`）——但**全仓库没有任何一行代码写入它**。写入只有 `'ACTIVE'`（`repository/flight.go:124`）和 `'RELEASED'`（`:163`）。

这说明设计时预想的是**两阶段模型**：座位先预留住 → 用户去支付 → 支付超时则自动过期释放。而当前实现是下单即 `CONFIRMED`，没有支付环节，也就没有超时释放。

**这个字段是一份没被执行的设计意图的化石。** 它值得留着——它标记了这个系统本该有但还没有的那一步。

**🔧 可以更好**
- **立刻**（问题 1 是正确性缺陷）→ `ReleaseReservation` 的第一个 `SELECT` 加 `FOR UPDATE`，让并发取消串行化；或者把 `UPDATE seat_reservations SET status='RELEASED' WHERE id=$1 AND status='ACTIVE'` 提到最前面，**用受影响行数判断是否该继续**（0 行说明别人已经释放过了，直接返回）。**代价**：前者增加持锁窗口；后者改变了语句顺序，需要确认"先标记后加座"在中途失败时的表现（同一事务内，回滚一起回滚，安全）。**后者更好，因为它把幂等性变成了一次原子的状态迁移，而不是靠锁。**
- **当"取消成功但座位没还"变得可观测时** → 问题 2 的两条路：要么改成失败即返回错误（用户重试，但取消不掉订单的体验很差），要么保持 best-effort 但**把失败的释放放进重试队列**。**代价**：后者需要持久化待补偿操作，和 5.3 的 Saga 是同一套基础设施——两个问题应该用同一个方案解决，不要各修各的。
- **当业务需要支付环节时** → 启用 `EXPIRED`：`ReserveSeats` 后订单进入 `PENDING`，加一个定时任务扫描超时的 ACTIVE 预留并释放。**代价**：(a) 需要定时任务和它自己的并发控制（多实例下不能重复扫）；(b) 超时时长是业务决策，太短用户付不完款，太长座位被长期占用；(c) 订单状态机从 2 态变成 4 态以上，所有依赖 `status` 的逻辑都要改。

## 5.5 这一章保证了什么、保证不了什么

一张表收尾——**这是我遇到线上问题时要先看的清单**：

| 场景 | 当前是否安全 | 靠什么保证 |
|---|---|---|
| 两个人抢最后一个座位 | ✅ 安全 | `SELECT ... FOR UPDATE` 串行化（5.1） |
| 应用层扣减逻辑写出 bug 导致负库存 | ✅ 安全 | `CHECK (available_seats >= 0)` 兜底（5.1） |
| gRPC 重试导致重复扣库存 | ✅ 安全 | `booking_id UNIQUE` + 事务回滚（5.2） |
| **客户端重发 POST /bookings** | ❌ **不安全** | 无——每次生成新 `booking_id`（5.2 📍） |
| 扣库存成功、写订单失败 | ❌ 不安全 | 无——座位永久泄漏（5.3，D-06） |
| **并发取消同一订单** | ❌ **不安全** | 无——座位可能被归还两次（5.4 问题 1） |
| **取消时释放失败** | ❌ **不安全** | 无——静默吞掉，订单已取消但座位没还（5.4 问题 2） |
| 预留长期占用不释放 | ❌ 不安全 | 无——`EXPIRED` 无生产者（5.4 问题 3） |
| 下游卡死拖垮上游 | ❌ 不安全 | 无——全链路无超时（2.3 📍） |

**四个 ✅ 全部集中在"单个数据库事务内部"，八个 ❌ 里有六个跨越了事务边界或进程边界。**

这不是巧合，是这一章真正要传达的结论：**PostgreSQL 的事务把它管辖范围内的一切都保护得很好；一旦跨出这个范围，就没有任何东西是自动安全的，每一条正确性都得手写。** 拆微服务买来的复杂度，绝大部分要在这里付账。

# 第 6 章：缓存

## 6.0 先问：为什么需要缓存

1.3 的规模里，**读写比是 20:1**——平峰 500 QPS 里约 475 次是查航班，25 次是下单。尖峰时读的绝对量更大。

而这些读有个关键性质：**它们高度重复**。3 万人抢同一个航班，就是 3 万次几乎相同的 `GetFlight(同一个 id)`。如果每一次都打到 PostgreSQL，数据库要为完全相同的答案重复工作 3 万次——而且这些读会和写路径的 `FOR UPDATE` 事务抢同一个连接池、同一份 CPU。

**缓存在这里的真正作用不是"让读变快"，是"把读挪开，好让写有资源可用"。** 这个视角很重要：如果只把缓存当性能优化，你会在缓存出问题时倾向于"关掉它先跑着"；但如果知道它是在保护写路径，你就知道关掉它意味着什么。

## 6.1 为什么是 Cache-Aside

**S · 处境**
航班信息读多写少：读是每秒数千次，写只在下单/取消时发生。

**T · 要求**
- 缓存不可用时系统要能继续工作（降级），不能变成新的单点（R4）
- 库存变化后，缓存里的旧值不能长期存在——**用户看到"还剩 5 座"结果下单失败，比看到"已售罄"更糟**

**A · 做法**
Cache-Aside（旁路缓存），逻辑全在应用层（`flight-service/internal/service/flight.go:27-79`）：

```
读：查 Redis → 命中则返回 → 未命中查 PG → 回填 Redis（TTL 5min）→ 返回
写：先写 PG（事务提交）→ 再删除相关缓存键
```

*为什么写是"删除"而不是"更新"*：更新缓存需要在写完 PG 后把新值算出来再写进去，而两个并发的写会产生**写覆盖竞争**——后提交的事务可能先写缓存，导致缓存里留下更旧的值。删除没有这个问题：删完之后下一次读会从 PG 重新加载权威值。**"让缓存失效"比"让缓存正确"容易得多，而且更不容易错。**

*为什么不是 Write-Through / Write-Behind*：Write-Through 要求缓存层承担写入职责，缓存挂了写也挂了——违反 R4。Write-Behind（先写缓存后异步落库）会让缓存成为库存的**真相来源**，而库存是 R1 保护的对象，绝不能放在一个可能丢数据的地方。

*为什么缓存放在 flight-service 而不是 booking-service*：缓存必须紧贴数据的所有权方。放在 booking-service 的话，flight-service 改了库存，booking-service 的缓存不知道——**失效逻辑会跨服务，那是缓存一致性最容易出事的形态**。

**R · 代价与边界**
- **存在不一致窗口**：PG 提交完成到缓存删除完成之间，读会拿到旧值。窗口很短（一次 Redis DEL），但非零
- 更糟的是：如果进程在这个窗口里崩溃，**旧值会一直活到 TTL 到期（5 分钟）**
- 三个经典缓存问题（穿透/击穿/雪崩）都不会自动被解决，见 6.3
- 失效边界：当写频率接近读频率时，缓存的命中率会崩塌，此时它只增加复杂度不提供收益

**📍 当前实现**
- 读路径：`service/flight.go:27-52`（Search）、`:54-79`（GetFlight），标准 Cache-Aside
- 失效路径：`ReserveSeats` / `ReleaseReservation` 成功后调 `invalidateFlightCache`（`:88`、`:100`）
- **失效发生在事务提交之后、且在事务之外**——不一致窗口如上
- **失效失败被静默忽略**：`InvalidateFlight` 里 `c.client.Del(ctx, key)` **不检查返回错误**（`cache/redis.go:83`）。Redis 抖动导致 DEL 失败，旧的 `available_seats` 会活满 5 分钟，而且没有任何日志、指标或告警会提到这件事
- **失效路径上多了一次数据库查询**：`invalidateFlightCache` 为了拿到 origin/destination/date 去做 search 缓存失效，又查了一次 `GetFlightByID`（`service/flight.go:114`）。这次查询失败时只记一条日志然后 `return`（`:116-117`）——**search 缓存就不失效了**

**🔧 可以更好**
- **当"下单时显示的余位不准"成为投诉来源时** → 先加指标：缓存命中率、DEL 失败次数。CLAUDE.md 第 4 节明文要求"每个韧性组件都要有指标——没有指标的机制等于不存在"，而**缓存当前一个指标都没有**，只有 `log.Printf`。**代价**：几乎为零，这是应该立刻做的。
- **当不一致窗口需要收窄时** → 延迟双删（写完删一次，隔几百毫秒再删一次），或者订阅数据库变更（CDC）来驱动失效。**代价**：延迟双删需要一个延迟任务，进程崩溃时第二次删除会丢；CDC 引入新组件和新的运维负担。**在当前规模下两者都不划算——先把 DEL 失败变得可观测更重要。**

## 6.2 缓存键怎么设计

两组键（`cache/redis.go:50-56`）：

| 键 | TTL | 存什么 |
|---|---|---|
| `flight:{uuid}` | 5 分钟 | 单个航班的完整 JSON |
| `search:{origin}:{destination}:{date}` | 5 分钟 | 搜索结果列表的 JSON |

**为什么键里要带全部查询参数**：缓存键必须唯一确定一个答案。`search:MOW:LED:2026-08-20` 和 `search:MOW:LED:2026-08-21` 是两个不同的问题，不能共用一个答案。

**为什么 TTL 是 5 分钟而不是更长或更短**：这是个**兜底值**，不是主要的一致性手段——主要手段是写操作后的显式删除。TTL 的作用是"万一删除失败了，最多错 5 分钟"。选 5 分钟是在"错误窗口"和"数据库压力"之间的一个折中，**它没有实测依据，是个拍出来的数**。

**失效时删哪些键**（`cache/redis.go:112-123`）：删精确的 `search:{o}:{d}:{date}`，再删无日期变体 `search:{o}:{d}:`。这两个删除覆盖了当前 `SearchFlights` 能产生的所有键形态——因为一个航班只属于一个日期，且 date 参数要么是具体日期要么是空。

**这个覆盖是脆弱的**：它依赖"搜索参数只有这三个、且 date 只有两种形态"这个前提。一旦 `SearchFlights` 增加参数（比如舱位、航司过滤），键的形态就会爆炸，而失效逻辑不会自动跟上——**缓存键的组合数一旦超过能穷举删除的范围，Cache-Aside 的显式失效就走到头了**，那时只能靠 TTL 或者改用带版本号的键。

## 6.3 三个经典问题：当前一个都没防

这三个问题在 1.3 的尖峰场景下全部会被触发，值得逐个说清楚。

### 穿透：查询不存在的数据

**现象**：`GetFlight(不存在的 UUID)` → 缓存 MISS → 查 PG → 不存在 → 返回 `NOT_FOUND`。**空结果不会被缓存**（`service/flight.go:66-69`：`err != nil` 就直接 return，跳过了回填）。

**后果**：用随机 UUID 反复请求，每一次都会穿过缓存打到数据库。这是一条**不需要任何权限就能用的数据库压力放大器**——攻击者用几乎为零的成本让数据库承担全部读负载。

**🔧 当入口暴露在公网时** → 缓存空值（用一个短 TTL 的哨兵值，比如 30 秒），或者用布隆过滤器拦掉不存在的 ID。**代价**：缓存空值会让"航班刚被创建"的场景有最多 30 秒的延迟可见性；布隆过滤器有误判率且需要在航班变更时重建。

### 击穿：热点键过期的瞬间

**现象**：`flight:{热门航班}` 的 TTL 到期，或者被一次下单删掉。此时**并发的数千个读请求同时 MISS**，全部涌向数据库查同一行。

**后果**：数据库瞬间承受尖峰的全部读压力。而这个时刻恰恰是写路径最需要数据库资源的时候（有人在下单才会触发失效）——**缓存失效和写压力峰值是同时发生的，它们互相放大**。

这是 1.3 尖峰场景下最可能先炸的地方：每一次成功下单都会删掉热门航班的缓存，而下单每秒发生数百次 → **缓存实际上处于"持续被删"的状态，命中率接近 0**。

**🔧 当单航班读 QPS 超过数百时** → 用 singleflight（Go 标准库 `golang.org/x/sync/singleflight`）合并同一个键的并发回源，只让一个请求打到数据库，其余等它的结果。**代价**：几乎为零，这是本章性价比最高的改动。**但它治不了"持续被删"**——那个要靠减少失效频率（比如失效改成更新而非删除，接受写覆盖风险）或者接受读到略旧的余位。

### 雪崩：大量键同时过期

**现象**：TTL 是固定的 5 分钟，没有随机抖动。服务重启后集中回填的一批键，会在 5 分钟后**同时过期**。

**后果**：周期性的数据库压力尖峰。

**🔧 当缓存键数量上千时** → TTL 加随机抖动（比如 5 分钟 ± 30 秒）。**代价**：几乎为零。当前只有 3 个航班，这个问题不会显现，但改动成本也几乎为零。

## 6.4 降级：Redis 挂了会怎样

**运行期**：Redis 挂掉后，`GetFlight` 的 `c.client.Get` 返回 error → 被当成 MISS（`cache/redis.go:62-65`）→ 查 PG → 尝试回填（也失败）→ 正常返回结果。**功能上完全降级成功，系统继续工作。**

**但有两个隐藏代价**：

1. **每个请求都会先尝试一次 Redis 操作**——连接失败或超时都要耗时间。Redis "慢"（而不是"挂"）时，这个开销会直接加在每一个请求的延迟上，而且**没有任何熔断保护**。第 7 章的熔断器只保护 gRPC 调用，不保护 Redis。
2. **数据库要承受全部读负载**。按 6.0 的分析，缓存挂掉意味着 475 QPS 的读全部落到 PG，同时和写路径抢 `pgxpool` 的 12 个连接（5.1 📍）。**这很可能直接把写路径拖垮。**

**启动期完全不降级**：`flight-service/cmd/main.go:53-56` 里，Redis 连接失败是 `log.Fatalf`——**服务直接起不来**。

这个不对称值得记住：**运行中 Redis 挂掉没事，但如果这时候服务重启，它就再也起不来了。** 而"服务出问题→重启试试"恰恰是运维最常见的第一反应。**Redis 故障 + 一次重启 = flight-service 彻底不可用**，这是 R4 明确要防的形态。

**🔧 立刻** → 把启动期的 Redis 连接失败从 `Fatalf` 改成"记录 Warn 并以无缓存模式启动"（`s.cache == nil` 的分支本来就完整支持这个）。**代价**：无缓存模式启动后，Redis 恢复了服务也不会自动接上，需要重启或者加重连逻辑——所以还要配一个"当前是否在无缓存模式"的指标和告警，否则会出现"服务悄悄降级运行了三天没人知道"。已登记：[D-22](../tasks/D-22-redis-startup-not-degradable.md)。

# 第 7 章：失败传播与韧性

> 本章的全部机制都在 booking-service 侧，因为它是唯一一个有下游的服务。
>
> 主题只有一个：**下游出问题时，上游怎么办。** R4 是本章的唯一驱动力。

## 7.0 失败会怎么传播

先把因果链画出来——**这条链是本章所有机制要打断的东西**：

```
flight-service 变慢（比如 5.1 的行锁排队）
   ↓ booking-service 的请求开始堆积（无超时 → 永远不放弃）
   ↓ goroutine 数量上升、内存上升
   ↓ HTTP 连接被占满
   ↓ booking-service 对所有请求都无响应 —— 包括「查订单」这种根本不需要 flight-service 的请求
   ↓ 用户看到的是「整个网站挂了」
```

**关键观察：故障从一个功能（下单）扩散到了所有功能（包括查订单）。** 这就是"失败传播"，也是为什么韧性机制的价值不在于"让失败的功能恢复"，而在于**把失败关在它自己的范围里**。

## 7.1 重试：只重试有意义的错误

**S · 处境**
两个服务之间每天几十万次 gRPC 调用。网络抖动、服务重启、瞬时过载都会让个别调用失败，而这些失败**下一秒重试就会成功**。

**T · 要求**
- 瞬时故障不应该变成用户可见的错误（R3）
- **重试必须安全**——不能因为重试而重复扣库存（依赖 5.2 的幂等）
- 重试不能把已经过载的下游压垮

**A · 做法**
1 次初始调用 + 最多 3 次重试，退避 100/200/400ms（`grpcclient/flight.go:19-20`）。**只重试两种 code**（`:24-27`）：

| code | 重试？ | 为什么 |
|---|---|---|
| `UNAVAILABLE` | ✅ | 下游不可达——可能只是在重启，下次可能就好了 |
| `DEADLINE_EXCEEDED` | ✅ | 超时——可能只是这一次慢 |
| `NOT_FOUND` | ❌ | 航班不存在，重试一万次还是不存在 |
| `RESOURCE_EXHAUSTED` | ❌ | 座位卖完了，重试不会变多 |
| `INVALID_ARGUMENT` | ❌ | 参数错了，重试不会让它变对 |
| `UNAUTHENTICATED` | ❌ | key 错了，重试不会让它变对 |

**分类的判据只有一句话：重试有没有可能得到不同的结果。** 答"不可能"的，重试纯粹是浪费——而且不是免费的浪费：在下游已经过载时，无差别重试会让请求量翻 4 倍，**把"慢"变成"死"**。

*为什么是指数退避而不是固定间隔*：固定间隔会让所有失败的客户端在同一时刻一起重试，形成同步的脉冲。指数退避把重试摊开。（理想情况还应该加随机抖动来打散同步性，当前没有。）

*为什么重试放在客户端而不是服务端*：服务端不知道操作是否幂等，也不知道调用方还愿不愿意等。**重试是调用方的决定。**

**R · 代价与边界**
- 最坏情况下一次调用变成 4 次，总耗时增加 700ms 的退避——在 R2 的 500ms 预算下，**一次重试就已经超预算了**
- 重试会放大下游压力：4 倍请求量打在一个已经不健康的服务上
- **完全依赖幂等**：5.2 一旦失效，重试就从"保护"变成"事故放大器"

**📍 当前实现**
- `grpcclient/flight.go:75-100`，分类正确、退避正确
- **`DEADLINE_EXCEEDED` 这个分支永远不会被触发**——全链路没有任何 `context.WithTimeout`（见 2.3 📍）。也就是说，重试实际上只对 `UNAVAILABLE` 生效
- **退避没有随机抖动**，多个并发请求的重试时刻是同步的
- **重试次数没有指标**——你无法知道系统当前有多少请求正在重试。CLAUDE.md 第 4 节明文要求"每个韧性组件都要有指标"

**🔧 可以更好**
- **和 2.3 的超时一起做**（这两件事必须一起做，否则各自都没意义）→ 加超时后 `DEADLINE_EXCEEDED` 才有意义，同时要重新核算"超时 × (1+重试次数) + 退避总和"是否还在 R2 预算内。**代价**：算下来很可能会发现 3 次重试太多——在 500ms 预算下，一次超时 150ms + 一次重试，就已经用掉 400ms。**重试次数是被延迟预算决定的，不是拍脑袋定的。**
- **当能观察到重试量时** → 退避加抖动。**代价**：几乎为零。

## 7.2 熔断器：不要对着尸体重试

**S · 处境**
下游彻底挂了（不是抖动，是持续不可用）。此时每一个请求都会：等待 → 失败 → 重试 3 次 → 最终失败。用户等了很久，得到一个错误，而且这个过程消耗了上游的连接和 goroutine。

**T · 要求**
- 下游确认不可用时，**立刻失败**而不是慢慢失败（R4）
- 下游恢复后要能**自动**恢复调用，不需要人工干预

**A · 做法**
三态机（`booking-service/internal/circuitbreaker/breaker.go`）：

```
        失败数 ≥ 阈值(5) 在窗口(60s)内
CLOSED ──────────────────────────────► OPEN
   ▲                                     │
   │ 探测成功                   保持 30s  │
   │                                     ▼
   └──────────────────────────────── HALF_OPEN
              探测失败 → 回到 OPEN
```

参数由环境变量注入（`booking-service/cmd/main.go:60-62`）：`CB_ERROR_THRESHOLD=5`、`CB_TIMEOUT_SECONDS=30`、`CB_WINDOW_SECONDS=60`。

OPEN 状态下调用直接返回 `ErrCircuitOpen`，handler 把它映射成 **HTTP 503**（`handler/booking.go:20-26`）——这是 3.3 里唯一映射正确的非 2xx 情况。

*为什么"快速失败"比"慢慢失败"好*：两者对用户都是失败，但快速失败**不消耗上游资源**。7.0 那条传播链里，把上游拖死的是"堆积"，而堆积来自"等待"。熔断器是专门用来打断这一环的。

*为什么需要 HALF_OPEN 这个中间态*：如果 OPEN 之后直接回到 CLOSED，全部流量会瞬间涌向刚恢复的下游，很可能立刻把它再压垮（**惊群**）。HALF_OPEN 的设计意图是"先放一个请求去探路"。

*为什么熔断器是独立包 + 泛型包装函数*（`withCircuitBreaker[T]`，`grpcclient/flight.go:59`）：韧性策略应该能独立于业务演进和测试。当前它有独立的单元测试（`circuitbreaker/breaker_test.go`）覆盖状态迁移——这是对的。

**R · 代价与边界**
- 熔断器打开期间，**即使下游其实是好的（误判），所有请求也会失败**
- 阈值的选择是个真实的两难：太敏感 → 抖动就熔断，可用性反而下降；太迟钝 → 起不到保护作用
- 熔断是**进程级**的：多实例部署时每个实例各有各的判断，恢复时机不一致

**📍 当前实现**

三个问题：

**问题 1：HALF_OPEN 状态不限流**（[D-21](../tasks/D-21-half-open-no-probe-limit.md)）

```go
case HalfOpen:
    return nil // allow the probe request
```

注释说"放行探测请求"（单数），但**代码对所有并发请求都返回 nil**——没有任何计数限制。尖峰时从 OPEN 转入 HALF_OPEN 的那一瞬间，**成千上万个请求会一起涌向刚刚恢复的下游**。

这恰恰是 HALF_OPEN 被发明出来要防止的事。当前的实现让这个状态**只起到了"延迟 30 秒"的作用，没起到"限流探测"的作用**。位置：`circuitbreaker/breaker.go` 的 `Allow()`。

**问题 2：熔断器没有任何指标**

状态迁移只有 `log.Printf("[CIRCUIT-BREAKER] %s → %s")`。**你无法在 Grafana 上看到熔断器什么时候开过、开了多久、拦掉了多少请求。**

CLAUDE.md 第 4 节写得很直接：*"每个韧性组件都要有指标——没有指标的机制等于不存在。"* 按这条标准，**当前的熔断器不存在**。

这一条已经包含在 [D-01](../tasks/D-01-circuit-breaker-error-classification.md) 的修法和验收标准里（状态 gauge + 迁移 counter），不是独立任务。

**问题 3：CLOSED 状态下成功不抵消失败**

`RecordSuccess` 只在 HALF_OPEN 时重置计数（`breaker.go` 的 `RecordSuccess`）。CLOSED 状态下，成功调用**不会**减少 `errorCount`，计数只在窗口过期时清零。

所以阈值的真实语义是"**窗口内累计 5 次失败**"，而不是"错误率超过某个比例"。在 1.3 的规模下——平峰 25 次下单/秒，60 秒窗口内约 1500 次调用——**5 次失败意味着 0.33% 的错误率就会触发熔断**。这个灵敏度对一个高吞吐服务来说过高了。

另外还有 **D-01**（业务错误被计入熔断统计）：`withCircuitBreaker` 里 `if err != nil { cb.RecordFailure() }`，而 `NOT_FOUND`、`RESOURCE_EXHAUSTED` 都是 `err != nil`。**尖峰时"座位卖完了"会大量返回 `RESOURCE_EXHAUSTED`，几秒钟就能把熔断器打开**——然后连查航班都不能用了。这是 1.3 场景下最容易先炸的第二个地方（第一个是 6.3 的缓存击穿）。

**🔧 可以更好**
- **和 D-01 一起做**（问题 3 和 D-01 是同一处代码，同一个原因）→ 只有"下游不可用"类的错误才 `RecordFailure`，判据和 7.1 的 `retryableCodes` 一致；同时把阈值从"绝对次数"改成"窗口内错误率 + 最小样本数"。**代价**：错误率型阈值需要维护窗口内的成功计数，实现复杂度上升；且"最小样本数"引入了新参数，低流量时熔断器会变迟钝。
- **立刻**（问题 2 是 CLAUDE.md 明文规则）→ 加三个指标：`circuit_breaker_state`（gauge，0/1/2）、`circuit_breaker_transitions_total`（counter，带 from/to 标签）、`circuit_breaker_rejected_total`（counter）。**代价**：几乎为零。**没有这些指标，第 8 章的告警就无法回答"服务错误率上升是因为下游挂了还是熔断器误判"。**
- **修问题 1** → HALF_OPEN 状态加一个"已放行探测数"计数器，只放行 1 个（或 N 个），其余仍然返回 `ErrCircuitOpen`。**代价**：需要处理"探测请求一直不返回"的情况，否则熔断器会卡在 HALF_OPEN 且永不放行——需要给探测本身设超时。**这又一次指回了 2.3 的"没有超时"。**

## 7.3 服务间认证

**S · 处境**
flight-service 的 gRPC 端口在容器网络里是开放的。任何能访问这个网络的东西都能调 `ReserveSeats` 直接扣座位。

**T · 要求**
- 只有 booking-service 能调用 flight-service（这是 2.1"库存唯一仲裁者"的执行手段）

**A · 做法**
booking-service 在 gRPC metadata 里附 `x-api-key`（`grpcclient/flight.go:50-52`），flight-service 用 unary 拦截器对**所有方法**校验（`flight-service/internal/auth/interceptor.go`），不匹配返回 `UNAUTHENTICATED`。

*为什么是拦截器而不是每个 handler 自己检查*：拦截器**默认覆盖所有方法**，新增 RPC 时不会忘记加保护。"忘了加"是这类检查最常见的失败模式，用拦截器把它变成不可能。

*为什么不是 mTLS*：mTLS 是正确的方向（D-08），它同时解决身份认证和传输加密。API key 的问题是它是**共享秘密**——泄漏了就得两边同时轮换，而且明文传输时任何能抓包的人都能拿到。

**R · 代价与边界**
- key 是共享秘密，轮换需要协调两个服务
- **明文传输**（`grpcclient/flight.go:37` 用 `insecure.NewCredentials()`），能抓包就能拿到 key（D-08）
- 拦截器对所有方法生效，包括将来可能需要公开的健康检查——`grpc_health_v1` 如果被加上，会被这个拦截器一起拦掉（这会和 D-05 的健康检查冲突）

**📍 当前实现**
- **默认配置下认证形同虚设**：`AUTH_API_KEY` 的默认值是空字符串（两个服务的 `main.go` 都是 `envOrDefault("AUTH_API_KEY", "")`）。两边都不配置时，booking-service 发送 `x-api-key: ""`，flight-service 比较 `"" == ""` → **通过**。
  安全机制在默认配置下静默失效，而且**没有任何警告**——这比"没有认证"更危险，因为它看起来是有保护的
- **拦截器顺序导致认证失败会污染 SLI**：`main.go:83-86` 里 metrics 拦截器在 auth 拦截器**之前**，所以被拒绝的请求也会计入 `http_requests_total` 和 `http_request_errors_total`。配错 key 会表现为错误率飙升 → 触发 `HighErrorRate` 告警（这个方向其实是对的，但它和真实故障混在一起了）
- 每次调用打一条 `[AUTH] OK` 日志——正常请求路径上的日志，违反 CLAUDE.md 第 4 节

**🔧 可以更好**
- **立刻** → `AUTH_API_KEY` 为空时启动即拒绝（`log.Fatal`），或者至少打一条 Warn 并暴露一个 `auth_disabled=1` 的指标。**代价**：本地 `go run` 不配环境变量就跑不起来了，违反 CLAUDE.md 第 4 节"代码默认值保证本地能直接 `go run`"的原则——**折中方案是保留默认值但强制打 Warn + 指标**，让"降级运行"可见而不是可静默。
- **当传输可能被监听时** → mTLS（D-08）。**代价**：证书的签发、分发、轮换是一整套运维工作；本地开发和 CI 都要能拿到证书，否则开发体验会崩。

## 7.4 Redis 的运行时拓扑

> 这一节讲的是**Redis 自己怎么活下来**，不是"缓存为什么存在"（那是第 6 章）。这是两类不同的问题：前者是运维拓扑，后者是应用设计。

**S · 处境**
Redis 是单进程的。它挂了，按 6.4 的分析，读负载会全部压到 PostgreSQL 并很可能拖垮写路径。

**T · 要求**
- Redis 主节点故障时能自动切换，不需要人工介入、不需要重启应用（R4）

**A · 做法**
Sentinel 模式。客户端用 `redis.NewFailoverClient`（`cache/redis.go:24-27`）——它不直连 master，而是**先问 sentinel"master 在哪"**，然后连过去。master 挂了，sentinel 选出新 master，客户端跟着切换。

*为什么不是客户端直连 master*：那样 master 的地址就写死在配置里，故障切换必须改配置 + 重启应用。

*为什么不是 Redis Cluster*：Cluster 解决的是**数据分片**（单机装不下），而这里的问题是**可用性**。当前缓存的数据量极小（几个航班的 JSON），分片毫无意义，而 Cluster 的运维复杂度高得多。

**R · 代价与边界**
- 故障切换期间（`down-after-milliseconds` + 选举时间）缓存不可用，走 6.4 的降级路径
- Sentinel 本身成为一个需要保证可用性的组件

**📍 当前实现**

配置（`redis/sentinel.conf`）：

```
sentinel monitor mymaster redis-master 6379 1     ← quorum = 1
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 10000
```

拓扑是 **1 master + 1 replica + 1 sentinel，quorum=1**。这个配置**不构成高可用**（D-04），原因有两条，第二条更严重：

1. **quorum=1 + 单个 sentinel = 没有仲裁**。Sentinel 的多数派机制是用来防止误判的：网络分区时，如果只有一个 sentinel 看不见 master，它不应该单方面决定切换。quorum=1 意味着**这唯一的一票就是全部**——网络抖动就可能触发一次不必要的 failover。
2. **Sentinel 自己是单点，而且是致命的单点**。客户端配置里只有一个 sentinel 地址（`cache/redis.go:26`：`SentinelAddrs: []string{sentinelAddr}`）。**sentinel 挂了，客户端连 master 在哪都问不到**——此时即使 Redis master 完好无损，缓存也彻底不可用。

**换句话说：引入 Sentinel 本意是消除单点，实际结果是把单点从 Redis master 挪到了 sentinel 上，而且新的单点没有任何冗余。**

**🔧 可以更好**
- **当需要真正的高可用时** → 3 个 sentinel、quorum=2，客户端配置全部三个地址。**代价**：多两个容器。在这台 7.7 GiB 的机器上，13 个容器已经很挤了——Sentinel 进程本身很轻（几 MB），但这是一台机器上的三个进程，**同机部署的三个 sentinel 防不了宿主机故障，只能防进程崩溃和 Redis 自身故障**。要真正高可用需要跨机器，而那超出了当前的部署形态。**这是"在单机上模拟高可用"的固有天花板，值得知道但不必假装解决。** 相关：D-04。

# 第 8 章：系统怎么被观察和守护

> 本章**不重复清单**——有哪些指标、CI 有哪几个 job，`docs/architecture/capabilities.md` 已经写了。
>
> 本章只回答四个"为什么"：为什么 SLI 选这两个、为什么指标要这么命名、为什么告警只有三条、为什么 CI 要拦性能退化。

## 8.1 为什么 SLI 是"可用性"和"p95 延迟"

**S · 处境**
系统有几十个可测量的数字：CPU、内存、连接数、缓存命中率、QPS、各种分位延迟。需要从中选出**判断"系统是否健康"的依据**。

**T · 要求**
- SLI 必须**从用户视角**定义——CPU 100% 但用户毫无感知，那不是故障
- 数量要少到能记住

**A · 做法**
两个 SLI：

| SLI | 定义 | SLO（目标值） |
|---|---|---|
| API 可用性 | `1 − 错误率(5m)` | 平峰 > 99% |
| API 延迟 | `p95(5m)` | 平峰 < 50ms，尖峰 < 500ms |

*为什么是这两个*：用户对一个 HTTP 服务只有两种不满——**"报错了"**和**"太慢了"**。其他所有指标（CPU、内存、连接数）都是**原因**，不是**症状**。SLI 应该测症状：CPU 打满但用户没感觉，不该告警；CPU 很闲但请求都超时，必须告警。

*为什么延迟用 p95 而不是平均值*：平均值会被少数极端值带偏，而且它不对应任何真实用户的体验。基线报告里有个完美的例子——`avg = 10.36ms` 比 `p99 = 8.60ms` 还大，因为有**一次** 8019ms 的请求把平均拉高了。**平均延迟"10ms"这个数字，不描述任何一个实际发生过的请求。**

*为什么不是 p99 或 p999*：分位越高，越能覆盖长尾，但也越容易被单个异常点触发而产生噪声告警。p95 是一个折中。**代价必须写清楚：p95 按定义会隐藏最慢的 5%。** 基线报告里那次 8 秒的请求，在 p95 上完全看不见——**可用性和 p95 都 PASS，但确实有一个用户等了 8 秒**。

**R · 代价与边界**
- p95 的盲区如上：5% 的最差体验被设计性地忽略
- 两个 SLI 都是**服务端视角**，不包含网络和客户端。用户实际感受到的延迟一定更大
- 5 分钟窗口意味着**短促的故障会被平滑掉**——一次持续 20 秒的完全不可用，在 5 分钟窗口里只体现为 6.7% 的错误率

**📍 当前实现**
- `scripts/verify_metrics.py` 在 CI 里查 Prometheus 验证这两个 SLI
- **只验 booking-service**，flight-service 的 SLI 无人验证
- **D-02：错误率把客户端错误算进去了**。`HighErrorRate` 用的是 `sum(rate(http_request_errors_total[5m]))`，而这个指标包含 `error_type="client_error"`（4xx，`booking-service/internal/metrics/metrics.go` 的 Middleware）。
  在 1.3 的尖峰场景下这是**致命的**：3 万人抢 300 座，注定有 2.97 万个 409（座位不足）。按当前定义，错误率会飙到 99%，告警全响——**而系统工作得完美无缺**。这不是"告警太吵"，是"SLI 定义错了"
- **直方图的桶和实际延迟量级不匹配**：桶是 `0.005, 0.01, 0.025, ...`，最小 5ms。而实测中位数 0.92ms、p95 4.38ms——**绝大多数请求都落在第一个桶里**。`histogram_quantile` 在桶内做线性插值，当 95% 的样本挤在同一个桶时，算出来的 p95 基本是编的。
  这直接影响 8.4 的 CI 门禁：**它验证的那个 p95 数字，精度不足以支撑"性能有没有退化"的判断**。已登记：[D-27](../tasks/D-27-histogram-buckets-mismatch.md)（区别于 D-16：那是容量问题，这是桶精度问题）
- **SLO 数字与场景不对应**：当前 SLO 是"p95 < 500ms"一个值，但 1.4 定的是平峰 50ms / 尖峰 500ms 两个值。**平峰用 500ms 意味着延迟涨到 10 倍都不会告警**

**🔧 可以更好**
- **修 D-02 时** → 错误率只算 5xx。**代价**：4xx 的异常上升（比如客户端集体传错参数、或者某个端点的校验逻辑写错了）就不会触发告警了，需要另建一条针对 4xx 突增的告警——**这两类错误需要不同的响应，本来就该分开看**。
- **当需要相信 p95 数字时** → 按实测分布重设桶，覆盖亚毫秒到几十毫秒：`0.0005, 0.001, 0.0025, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5`。**代价**：(a) 桶数量增加会线性增加时间序列数（每个桶一条序列 × 每个 endpoint × 每个 service），Prometheus 内存上涨，而这台机器只有 7.7 GiB；(b) **改桶会让历史数据不可比**——旧数据的桶边界不同，跨越改动时间点的 `histogram_quantile` 查询会失真。
- **当平峰和尖峰需要分别承诺时** → SLO 分场景定义，用不同的告警规则和不同的时间窗口。**代价**：需要一种方式区分"现在是平峰还是尖峰"，最简单的是按时间段（放票时刻已知），但那是硬编码；更通用的是按流量水位动态判断，复杂度显著上升。

## 8.2 为什么指标要跨协议统一命名、为什么标签要克制

**A · 做法**

flight-service 是 gRPC 服务，但它**刻意复用 `http_*` 指标名**（`flight-service/internal/metrics/metrics.go`，Help 文本里明确写了理由）。两个服务导出同名指标，用 `service` 标签区分。

*为什么*：这样**一条 PromQL 能同时覆盖两个服务**。如果 flight-service 用 `grpc_requests_total`，每一条告警规则、每一个看板 panel 都要写两遍，然后在其中一处忘记更新。**命名统一的收益是查询和告警的复用，代价是"http" 这个词在 gRPC 上下文里不准确**——这个代价被明确接受了。

**标签基数控制**——这是监控系统最常见的事故原因：

| 侧 | `endpoint` 标签的值 | 基数 |
|---|---|---|
| HTTP | `c.Path()` 路由模板 → `/bookings/:id` | 有界（6 个端点） |
| gRPC | `info.FullMethod` → `/flight.FlightService/GetFlight` | 有界（4 个方法） |

**如果用实际 URL**，每个订单 UUID 都会变成一个新的时间序列。20 万单/日 = 20 万条序列/日，Prometheus 内存会被打爆——**在这台 7.7 GiB 的机器上，几个小时就会 OOM**。

CLAUDE.md 第 4 节把这条写成了硬规则：*"加标签前先问：取值集合有上界吗？UUID / URL / 用户 ID / 错误消息作标签绝对禁止。"*

**📍 当前实现**
- 基数控制做对了：两侧都用模板/方法名
- `status` 标签：HTTP 侧是状态码字符串（有界），gRPC 侧是 `code.String()`（17 个值，有界）
- **`http_request_errors_total` 和 `http_requests_total{status!="OK"}` 语义重复**——前者是后者的子集，多存了一份。不是错误，但两个指标的口径必须人工保持一致，而 D-02 正是这种口径分歧的产物

## 8.3 为什么告警只有三条

**T · 要求**
CLAUDE.md 第 4 节给了唯一判据：**"这条告警响了，有人需要立刻做点什么吗？"** 答"不"的就该是看板上的一条线，不是告警。

**A · 做法**
三条（`prometheus/alerts.yml`）：

| 告警 | 触发 | 人要做什么 |
|---|---|---|
| `HighErrorRate` | 错误率 > 5% 持续 2m | 查日志找错误来源 |
| `HighLatencyP95` | p95 > 1s 持续 2m | 查是数据库慢、锁等待还是下游慢 |
| `ServiceDown` | target down > 1m | 服务挂了，查为什么没起来 |

*为什么不对 CPU / 内存 / 连接数告警*：它们是**原因**不是**症状**（见 8.1）。CPU 90% 但延迟正常、错误率为零——不需要任何人做任何事。**为原因告警会产生大量"响了但没事"的噪声，而噪声的终局是所有人都不再看告警。**

*为什么每条都有 `for: 2m`*：瞬时尖刺不该叫醒人。`for` 是在"响应速度"和"噪声"之间的旋钮。

**R · 代价与边界**
- 只覆盖症状意味着**故障发生后才知道**，没有预警。磁盘将满、连接池将耗尽这类"可预测的故障"不会提前告警
- 2 分钟的 `for` 意味着最快也要 2 分钟才知道

**📍 当前实现**
- **三条告警全部缺少 `runbook_url` 注解**，而 CLAUDE.md 第 4 节明文要求"必须带 `severity`、`sli` 标签和 `summary` / `description` / `runbook_url` 注解"。`docs/runbooks/` 目录当前是空的（D-14）
- **`ServiceDown` 只覆盖两个应用服务**：`up{job=~"booking-service|flight-service"}`。**数据库挂了、Redis 挂了、Prometheus 自己挂了，都不会告警**——而按 6.4 的分析，Redis 挂掉 + 一次重启 = flight-service 彻底起不来
- **Alertmanager 没有接任何通知渠道**（receiver 为空），告警只在 Web UI 里可见。**没人看的告警等于没有告警**（D-12）
- 熔断器没有指标（7.2 问题 2），所以**无法针对"熔断器打开"告警**——而这恰恰是最需要人立刻介入的信号之一

**🔧 可以更好**
- **补 `ServiceDown` 的覆盖面** → 改成 `up == 0`（覆盖全部 6 个 target），或者显式列出基础设施 job。**代价**：exporter 短暂抓取失败会误报，需要调 `for` 的时长；且不同组件的"挂了多久算故障"不一样——数据库挂 1 分钟是灾难，exporter 挂 1 分钟只是监控缺了个点。**一条规则套所有 target 会让阈值失去意义，应该分组设置。**
- **当熔断器有了指标后**（7.2 🔧）→ 加一条"熔断器持续 OPEN 超过 N 分钟"的告警。**代价**：需要先定义"多久算异常"——短暂熔断是保护机制正常工作，不该告警。

## 8.4 为什么 CI 要拦住性能退化

**S · 处境**
功能测试能拦住"改坏了"，但拦不住"改慢了"。一个 PR 可能让 p95 从 5ms 涨到 300ms，所有测试依然全绿。

**T · 要求**
- 性能退化和错误率上升要能**阻断合并**，而不是上线后才发现

**A · 做法**
CI 的 `load-test` job：起全栈 → 跑 k6 → `scripts/verify_metrics.py` 查 Prometheus 验证 SLI → 违反则 `exit 1`。

*为什么查 Prometheus 而不是直接看 k6 的输出*：k6 测的是**客户端视角**（含网络），Prometheus 测的是**服务端视角**。用服务端指标做门禁，验证的是"服务本身的性能"，不受压测机波动影响。**更重要的是：这条路径顺带验证了整套监控链路是通的**——指标被正确导出、被 Prometheus 抓到、PromQL 写对了。监控系统自己也需要被测试。

*为什么这是这套 CI 里最有价值的部分*：CLAUDE.md 第 1 节把"为了让 CI 变绿而放宽 SLO 阈值"列为永远不要做的事，理由是"门禁可以被绕过就不再是门禁"。**SLO 在这里不是文档里的一句承诺，是能卡住合并的代码。**

**R · 代价与边界**
- CI 时长显著增加（起 13 个容器 + 压测 + 查询）
- **门禁的可信度完全取决于压测的真实性**——见下方 📍
- GitHub Actions runner 的性能有波动，可能产生假阳性

**📍 当前实现**
- 四个 job：`build` / `unit` / `integration`（16 个 pytest 用例）/ `load-test`
- **压测负载不真实**：k6 有 `sleep(0.1)`，10 VU 的吞吐上限是 90 iter/s（见第 1 章 📍）。**门禁验证的是"系统在 1% 负载下没变慢"**——这能拦住灾难性退化（比如某个查询变成全表扫描），但拦不住"在真实负载下才暴露"的问题，比如锁竞争、连接池耗尽、缓存击穿
- 热点分散度也不真实：3 个航班随机挑，而 1.3 的场景是 1 个航班
- **p95 的数值精度不足**（见 8.1 📍 的桶问题），门禁比较的那个数字本身就不精确
- `verify_metrics.py` 只验 booking-service

**🔧 可以更好**
- **当需要门禁真的能拦住容量问题时** → 去掉 `sleep`、提高 VU、固定单航班，把阈值从 SLO 改成"相对上次基线的退化比例"。**代价**：(a) CI 时长和资源消耗上升；(b) GitHub runner 的性能波动会让"相对退化"产生假阳性，需要多次采样或放宽容差；(c) **真实负载下 5.4、6.3、7.2 那几个缺陷会立刻让 CI 变红**——这是好事，但意味着必须先修完它们，否则 CI 会长期红着，而长期红着的 CI 等于没有 CI。**这条 🔧 有明确的前置依赖，不能单独做。** 相关：D-16。

**跳 1/9 — booking-service 进程，Echo 中间件链**

**跳 2/9 — 路由与参数绑定**

**跳 3/9 — service 层，第一次 gRPC：`GetFlight`**
`booking-service/internal/service/booking.go:103` → `grpcclient/flight.go`

目的是**拿价格**，用来算 `total_price`。

调用被 `withCircuitBreaker[T]` 包裹（`grpcclient/flight.go:59`），执行顺序：

1. `cb.Allow()` —— 熔断器状态检查
   - **OPEN 且未到 30s** → 立即返回 `ErrCircuitOpen` → handler 映射成 **503**（`handler/booking.go:20-26`）。**这是全链路唯一一个映射正确的非 2xx 故障响应**
   - **OPEN 且已过 30s** → 转 HALF_OPEN 并放行。**注意：此时所有并发请求都会被放行**（7.2 问题 1）
2. `retry(...)` —— 最多 4 次尝试（1 + 3），退避 100/200/400ms
3. `metadata.AppendToOutgoingContext(ctx, "x-api-key", apiKey)` 附认证（`:50-52`）
4. 结果记入熔断器：`err != nil` 就 `RecordFailure()` —— **包括 `NOT_FOUND` 这类业务错误**（D-01）

**超时**：**无**。用的是 Echo 的 request context，没有 deadline。所以 `retryableCodes` 里的 `DEADLINE_EXCEEDED` 永远不会触发（2.3 📍）

**传输**：明文 HTTP/2，`insecure.NewCredentials()`（`:37`，D-08）

---

**跳 4/9 — flight-service 进程，拦截器链**
`flight-service/cmd/main.go:82-87`

顺序是 `metrics` → `auth`：

1. **metrics 拦截器先执行** → 即使认证失败，请求也会被计入 `http_requests_total` 和 `http_request_errors_total`（7.3 📍）
2. **auth 拦截器**校验 `x-api-key`
   - 无 metadata → `UNAUTHENTICATED`
   - key 不匹配 → `UNAUTHENTICATED` → booking-service 侧**不映射这个 code** → 落到默认分支 → **HTTP 500**（3.3 📍）
   - **两边都不配 `AUTH_API_KEY` 时，`"" == ""` 通过**（7.3 📍）
3. 每次通过都打一条 `[AUTH] OK` 日志

**跳 5/9 — flight-service service 层，Cache-Aside 读**
`flight-service/internal/service/flight.go:54-79`

```
GET flight:{uuid}   ← Redis（经 Sentinel 发现的 master）
```

**这里返回的 `price` 可能是最多 5 分钟前的**——`total_price` 快照的准确性受制于此（4.3 📍、5.3 📍）。

**空结果不缓存** → 用不存在的 UUID 反复请求可以持续穿透到数据库（6.3 穿透）

**观测**：`log.Printf("[CACHE] HIT/MISS ...")`（`cache/redis.go:63,66`）—— 正常路径上的非结构化日志，违反 CLAUDE.md 第 4 节。**没有任何缓存指标**

**跳 6/9 — 生成 booking_id**
`booking-service/internal/service/booking.go:120`

**跳 7/9 — 第二次 gRPC：`ReserveSeats` —— 全链路唯一持锁的地方**
`grpcclient` → flight-service → `repository/flight.go:81-131`

同样经过熔断器 + 重试 + 认证（同跳 3、4）。到达 repository 后，**单个数据库事务**：

```sql
BEGIN;
```

**7a. 幂等前置检查**（`:86-92`）
```sql
SELECT id, flight_id, booking_id, seat_count, status, created_at
FROM seat_reservations WHERE booking_id = $1 AND status = 'ACTIVE';
```
命中 → 直接 `return nil`，**不扣减**，事务提交。这是重试安全的第一层。

**7b. 悲观锁 —— 持锁窗口从这里开始**（`:99-101`）
```sql
SELECT available_seats FROM flights WHERE id = $1 FOR UPDATE;
```
- 同航班的其他事务在这里**全部排队**，直到本事务结束
- **无行** → `ErrNotFound` → `NOT_FOUND` → **HTTP 404**，不重试（不在 `retryableCodes` 里）
- **等锁没有超时**：`lock_timeout` 未设置，PostgreSQL 默认无限等待。撞上 5.1 的吞吐上限时，请求会在这里无限排队

**7c. 判断与扣减**（`:109-118`）
```sql
-- available < seatCount → ErrInsufficientSeats → RESOURCE_EXHAUSTED → HTTP 409
UPDATE flights SET available_seats = available_seats - $1 WHERE id = $2;
```
- `CHECK (available_seats >= 0)` 在此生效——应用层判断出错时的最后防线（5.1）
- **409 是正常业务结果，不是故障**。但当前它会被计入 `http_request_errors_total`（D-02），**尖峰时能把错误率推到 99%**；同时 `err != nil` 会被熔断器记为失败（D-01），**几秒内就能把熔断器打开**

**7d. 写预留记录**（`:121-126`）
```sql
INSERT INTO seat_reservations (flight_id, booking_id, seat_count, status)
VALUES ($1, $2, $3, 'ACTIVE') RETURNING ...;
```
- `booking_id UNIQUE` 在此生效：并发的同 ID 请求会在这里失败 → **整个事务回滚，连同 7c 的扣减一起撤销**（5.2）

```sql
COMMIT;   -- 持锁窗口到这里结束，约 1–3ms
```

**7e. 缓存失效**（`service/flight.go:88` → `:106-122`）—— **在事务之外**
```
DEL flight:{uuid}                        ← 返回值不检查（cache/redis.go:83）
SELECT ... FROM flights WHERE id=$1      ← 又查一次 PG，只为拿 origin/dest/date
DEL search:{o}:{d}:{date}
DEL search:{o}:{d}:
```
- **不一致窗口**：COMMIT 完成到 DEL 完成之间，读会拿到旧余位
- **DEL 失败静默**：旧值活满 5 分钟，无日志无指标（6.1 📍）
- 中间那次 `GetFlightByID` 失败 → 只记日志 `return` → **search 缓存不失效**

**观测**：gRPC metrics 拦截器记 `http_requests_total{service="flight-service", endpoint="/flight.FlightService/ReserveSeats", status="OK"}` + duration。**这个 duration 包含了 7b 的锁等待时间**——所以"下单变慢"会如实反映在 flight-service 的 p95 上，这是排查锁竞争的第一个信号。

**`GET /flights` （SearchFlights）**

**`GET /bookings/{id}` / `GET /bookings?user_id`**
**最简单的一条：完全不跨服务。** 跳 1–2 → 直接 `SELECT ... FROM bookings`（列表走 `idx_bookings_user`）→ 响应。**没有 gRPC、没有熔断、没有缓存、没有重试。**

值得单独看一眼，因为它是对照组：**当没有跨服务调用时，代码短得多，失败模式也只剩"数据库挂了"一种。** 第 5 章那八条 ❌ 里没有一条会发生在这条路径上。这就是 2.1 里"拆分买来的复杂度"的直观度量。

**`POST /bookings/{id}/cancel`**
跳 1–2 相同，然后：

1. `SELECT ... FROM bookings WHERE id=$1` → 无行 → **404**
2. `if b.Status == "CANCELLED"` → **409**。**这个检查没有加锁**（`service/booking.go:211`），两个并发取消都会通过
3. gRPC `ReleaseReservation`（经熔断器 + 重试 + 认证）
   ```sql
   BEGIN;
     SELECT ... FROM seat_reservations WHERE booking_id=$1 AND status='ACTIVE';  -- ⚠ 无 FOR UPDATE
     UPDATE flights SET available_seats = available_seats + $1 WHERE id=$2;
     UPDATE seat_reservations SET status='RELEASED' WHERE id=$1;
   COMMIT;
   ```
   **⚠ 并发取消会在这里重复归还座位**（5.4 问题 1）——两个事务都读到同一条 ACTIVE 记录，都执行加法。`chk_available_le_total` 只在航班坐满时才拦得住
4. 缓存失效（同跳 7e）
5. **⚠ 第 3 步失败时只记日志，不返回**（`service/booking.go:218-223`）→ 继续执行第 6 步
6. `UPDATE bookings SET status='CANCELLED'` → **200**

**所以取消路径有两个方向相反的危险**：并发时**多还**座位（步骤 3），下游故障时**不还**座位但告诉用户取消成功了（步骤 5）。

# 附录：类型选择检查表

> 这些理由跨表共享，所以不套 STAR。加新表新字段时回来查这张表。

## A.1 主键为什么是 UUID 而不是自增整数

| | UUID | `BIGSERIAL` |
|---|---|---|
| 生成位置 | **应用层或任意节点** | 数据库，需要一次往返 |
| 分布式唯一 | ✅ 天然 | ❌ 分库后会冲突 |
| 跨库引用 | ✅ 全局无歧义 | ⚠️ 两个库的 id=1 是不同东西 |
| 泄漏业务量 | ❌ 不泄漏 | ⚠️ `/bookings/1523` 直接告诉竞对你卖了多少单 |
| 索引体积 | 16 字节，随机分布 | 8 字节，顺序 |
| 写入局部性 | ⚠️ 随机，B-tree 页分裂多 | ✅ 顺序追加 |

在 1.3 的规模下，前四条全部成立而且都是刚需：

1. **`booking_id` 必须在调用 flight-service 之前就存在**（跳 6）——它是幂等键。用自增 ID 的话，ID 要等 `INSERT bookings` 之后才有，而那是跳 8，**顺序就反了**，5.3 的"先扣库存后落订单"根本无法实现
2. **两个库的 ID 不能撞**——`bookings.id` 和 `seat_reservations.booking_id` 跨库对应，自增序列各管各的，必然重号
3. 多实例部署时不需要中心化的发号器
4. 订单 ID 出现在 URL 里，不该泄漏业务量

代价（第 5、6 行）在这个数据量下不显著：`seat_reservations` 一年 7300 万行，B-tree 页分裂带来的写放大存在但不致命。**数据量再大一个数量级时，应该考虑时间有序的 UUID v7 或 ULID**——保留全局唯一，同时恢复写入局部性。

**默认值用 `gen_random_uuid()`**（三张表都是），但**实际写入时应用层几乎总是显式传 ID**——因为 ID 要先于插入存在（理由 1）。数据库默认值在这里是兜底，不是主路径。

## A.2 金额为什么是 BIGINT

`flights.price` 和 `bookings.total_price` 都是 `BIGINT`，存**最小货币单位**（分 / 戈比）。

*为什么不是 `FLOAT` / `DOUBLE`*：浮点数无法精确表示 0.1 这样的十进制小数。`0.1 + 0.2 != 0.3` 在金额计算上是灾难——对账时会出现几分钱的差额，而且**这种差额无法解释也无法修复**。

*为什么不是 `NUMERIC`/`DECIMAL`*：`NUMERIC` 精度正确，但它是变长类型，运算比整数慢，而且 Go 侧没有原生的十进制类型，要引入第三方库。**用整数存最小单位，是在"精确"和"简单"之间的标准做法。**

*代价*：所有展示层都必须记得除以 100。**这个约定必须写在契约里**——`openapi.yaml` 里 `price` 是 `type: integer`，但**没有任何注释说明它是分**。客户端开发者看到 `"price": 15000` 完全可能理解成 15000 元。这是个真实的接口设计缺陷，成本几乎为零但没做。

*上界*：`BIGINT` 是 8 字节，约 9.2×10^18 分 ≈ 9.2×10^16 元。`INT` 只到 21 亿分 ≈ 2100 万元——**单个订单不会超，但如果将来要存累计金额就会溢出**。用 `BIGINT` 是便宜的保险。

## A.3 状态为什么是 VARCHAR + CHECK

见 4.4。要点：`ENUM` 的迁移别扭，`SMALLINT` 牺牲可读性，`CHECK` 防的是静默的脏数据。

## A.4 时间类型：TIMESTAMP vs TIMESTAMPTZ

**这是本仓库唯一一处两个库做了矛盾选择的地方。**

| 字段 | 类型 | 库 |
|---|---|---|
| `flights.departure_time` / `arrival_time` | `TIMESTAMP`（无时区） | flight_db |
| `seat_reservations.created_at` | `TIMESTAMP`（无时区） | flight_db |
| `bookings.created_at` | **`TIMESTAMPTZ`**（带时区） | booking_db |

两者的区别不是"存不存时区"（`TIMESTAMPTZ` 也不存时区），而是**是否做时区转换**：`TIMESTAMPTZ` 写入时按会话时区转成 UTC 存储，读取时转回会话时区；`TIMESTAMP` 原样存、原样取。

**正确的选择取决于这个时间是什么**：

- **`created_at` 这类"事件发生的时刻"必须用 `TIMESTAMPTZ`**——它描述的是绝对时间轴上的一个点，跨时区必须一致。`bookings.created_at` 是对的
- **`seat_reservations.created_at` 用 `TIMESTAMP` 是错的**——它是同一类语义的字段，却做了相反的选择。将来做超时释放时（5.4 问题 3），"这条预留是 10 分钟前创建的吗"这个判断会依赖它，而服务器时区一旦变化，判断就会错
- **`departure_time` 用 `TIMESTAMP` 是可辩护的**——航班时刻在业务上通常表达为"当地时间 14:30"，不是绝对时刻。但这样的话，**必须另外存一个机场时区**才能算出绝对时间，而当前没有存。所以现在的语义实际上是模糊的：既不是当地时间（缺时区），也不是绝对时间（不转换）

**这个不一致的成因**是 2.2 📍 提到的：分库之后缺少统一规范。**它值得记住，因为它正是这份文档想防止的那类问题**——每个决定单独看都不算错，合起来就矛盾了，而且没有任何测试会发现。

**🔧 当要做超时释放、或者跨时区运营时** → 统一成 `TIMESTAMPTZ`（`departure_time` 另加机场时区列）。**代价**：迁移要处理已有数据的时区解释——`ALTER TYPE ... USING` 会按会话时区做转换，如果历史数据本来就是按 UTC 存的，转换会把它们整体平移。**这是那种"改的时候很容易，改错了很难发现"的迁移**，必须先在数据副本上验证。

## A.5 字符串长度上限

| 字段 | 长度 | 依据 |
|---|---|---|
| `origin` / `destination` | `VARCHAR(3)` | **IATA 机场三字码，国际标准**——长度精确等于标准，多一个字符都是脏数据 |
| `flight_number` | `VARCHAR(10)` | 航班号最长约 6–7 字符（2 字母 + 4 数字），留了余量 |
| `airline` | `VARCHAR(100)` | 展示字段，经验值 |
| `passenger_name` / `passenger_email` | `VARCHAR(200)` | 经验值 |
| `status` | `VARCHAR(20)` | 最长枚举值 `SCHEDULED` 是 9 字符，留余量 |

**为什么要设上限而不是用 `TEXT`**：在 PostgreSQL 里 `VARCHAR(n)` 和 `TEXT` 的**存储性能完全相同**，`VARCHAR(n)` 唯一的作用就是**长度校验**。所以设上限的理由不是省空间，是**防止异常数据静默进入**——一个 5000 字符的 `passenger_name` 一定是 bug 或攻击，让数据库直接拒绝它，比让它进库然后在某个展示页面炸掉要好。

**代价**：改长度需要 `ALTER TABLE`（加长是轻量操作，缩短要全表校验）。所以上限应该定得**宽松但有界**——`VARCHAR(200)` 而不是 `VARCHAR(50)`。

**唯一的例外是 `VARCHAR(3)`**：它不是"宽松的上限"，是"精确的标准"。这两种用法的意图完全不同，看到 `VARCHAR(3)` 应该立刻想到"这背后有个外部标准"。
