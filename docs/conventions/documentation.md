# 文档规范

> 这份文档说明 `docs/` 为什么这样分类、每类文档谁负责更新、什么时候更新。
>
> 变更纪律的通用部分在 [engineering.md](./engineering.md)，这里只讲文档。

## 1. 分类的依据

分类轴不是主题，而是 **「什么时候需要改这份文档」**。

按主题分类（"缓存相关的都放一起"）在文档变多之后必然失效，因为一个主题会同时包含"现在是什么"和"将来要做什么"，这两种东西的更新触发条件完全不同 —— 前者跟着代码走，后者跟着计划走，混在一个文件里就会出现"做完一条要在四百行文档里找位置划掉"的窘境。

| 类别 | 目录 | 时效性 | 更新触发条件 | 数量趋势 |
|---|---|---|---|---|
| **事实层** | `architecture/` | 永远描述当下 | 代码改了就得改 | 稳定 |
| **规范层** | `conventions/` | 永远描述当下 | 做法变了才改 | 稳定 |
| **意图层** | `plans/` `tasks/` | 描述未来 | 完成即消亡或归档 | 流动 |
| **知识层** | `knowledge/` | 与本仓库解耦 | 学到东西就写 | 只增不减 |
| **操作层** | `runbooks/` | 永远可执行 | 告警或系统变了就改 | 随告警数增长 |
| **记录层** | `reports/` | 冻结在某个时间点 | **永不修改**，只新增 | 只增不减 |

**记录层的"永不修改"是硬规则。** 一份复盘写的是"当时我们以为是 X，后来发现是 Y"，事后回去把它改成"就是 Y"，就毁掉了这份文档全部的价值 —— 它记录的不只是结论，是认知过程。发现记录有错，新写一份并在旧的里加一行指向新文档的链接。

## 2. 目录职责

```
docs/
├── README.md              导航
├── architecture/          系统现在是什么
│   ├── overview.md          运行时拓扑、数据流、边界、关键机制
│   ├── data-model.md        schema 与约束
│   ├── contracts.md         gRPC / REST 契约、错误码映射
│   └── capabilities.md      能力清单，每条指向代码位置
├── conventions/           动手前读
│   ├── engineering.md       分支、提交、配置、日志、告警、变更纪律
│   └── documentation.md     本文
├── plans/                 要做什么、为什么
│   ├── roadmap.md           分阶段路线图
│   └── gap-analysis.md      对标岗位的能力缺口（G-xx）
├── tasks/                 可执行条目，一条一文件
│   ├── README.md            看板索引
│   ├── D-xx-*.md            已发现的缺陷
│   └── done/                完成后移入
├── knowledge/             按主题的知识笔记
│   ├── kubernetes/ observability/ sre/ linux-network/ datastore/
├── runbooks/              一条告警一个文件
└── reports/               带日期，写完不改
    ├── postmortems/         YYYY-MM-DD-<事件>.md
    ├── load/                压测报告
    └── reviews/             周期性 SLO 评审
```

## 3. 三条硬规则

### 规则一：`architecture/` 里不出现尚未实现的东西

已经存在的写 `architecture/`，还不存在的写 `plans/` 或 `tasks/`。

架构文档里描述一个不存在的组件，比没有文档更有害 —— 读者会按它做决策。

### 规则二：改运行时行为的 PR 必须同时动 `tasks/` 和 `architecture/`

```
tasks/D-xx.md → tasks/done/D-xx.md（status 改 done）
architecture/capabilities.md 加一条，带代码位置
```

不允许"回头再补"。文档漂移是渐进的，每次都只漂一点，半年后整个 `docs/` 就只能当历史读物。

### 规则三：陈述系统行为必须给可核对的依据

代码路径加行号（`booking-service/internal/grpcclient/flight.go:66`）、配置文件位置、或可复现的命令。

不写"应该"、"大概"、"理论上"。写不出依据说明你没验证过，那就先去验证。

## 4. 编号与命名

| 对象 | 规则 | 例 |
|---|---|---|
| 普通文档 | kebab-case，**目录承担分类，不加全局序号** | `data-model.md` |
| 任务 | `<ID>-<kebab 描述>.md`，ID 稳定不复用 | `D-01-circuit-breaker-error-classification.md` |
| 复盘 | `YYYY-MM-DD-<事件>.md` | `2026-09-03-redis-failover.md` |
| 压测报告 | `YYYY-MM-DD-<场景>.md` | `2026-08-20-baseline.md` |
| Runbook | 与告警名完全一致 | `HighErrorRate.md` |

**为什么去掉 `01-` `02-` 这类前缀**：全局序号在文档跨目录移动后就失效了，而且插入一份新文档要么破坏序号连续性、要么重命名一片文件（连带所有链接失效）。目录名已经承担了分类和排序，序号是冗余的。

只有两类东西保留稳定 ID：**任务**（要被提交信息 `Refs: D-01` 引用）和 **ADR**（要被互相引用）。ID 一旦分配就不再复用，即使任务被取消。

## 5. 语言

`docs/` 全部用中文。

根目录 `README.md` 是课程交付物（俄语），受众是课程评分者，保持原样不动。它同时是仓库门面，等哪天需要改写时，把俄语版归档到 `docs/archive/`，而不是直接覆盖 —— 它是这个项目的起点记录。

## 6. 链接

- 用相对路径，不用绝对 URL（仓库改名或 fork 后仍然有效）
- 引用任务时链到具体文件，不要只写 "D-01"：`[D-01](../tasks/D-01-circuit-breaker-error-classification.md)`
- 引用代码时给路径加行号，行号会过期，所以**同时给出足够的上下文**（函数名 / 变量名），让读者在行号漂移后还能找到

## 7. 复盘文档的额外要求

- **对事不对人**（blameless）。根因是"系统允许这种错误发生"，不是"某人手滑"
- 必须有**时间线**：故障开始 → 检测到 → 定位 → 缓解 → 恢复，每个时间点都有
- 必须有**量化影响**：多少请求失败、持续多久、错误预算消耗了多少
- 必须有**可执行的行动项**，每条对应一个 `tasks/` 条目。"以后小心点"不是行动项
- 必须写下**假设与现实的差异** —— "我以为熔断器 5 秒内打开，实际用了 47 秒"，这是复盘里最有价值的部分

## 8. 给 AI 协作留的接口

任务文件带 YAML frontmatter（`id` / `severity` / `status` / `phase` / `blocks` / `refs`），是为了让"当前阶段有哪些未完成的 critical 任务"这类问题可以被机器回答，而不用通读全部文档。

新增字段前先问：这个字段会被谁读？没有读者的元数据只是维护负担。

项目级 `CLAUDE.md` 的规划见 [roadmap.md](../plans/roadmap.md) 阶段 6 与 [engineering.md § 10](./engineering.md)。
