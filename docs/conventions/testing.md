# 测试规范 —— 理由与例子

> **规则本身写在根目录 [`CLAUDE.md`](../../CLAUDE.md) § 4，那里是唯一权威。**
>
> 这份文档不重复规则，只回答"为什么是这条规则"，并列出**当前不覆盖什么**。冲突时以 `CLAUDE.md` 为准。
> 变更纪律的通用理由见 [engineering.md](./engineering.md)。

## 1. 为什么分档轴是"外部依赖"，不是"耗时"或"测试对象"

按耗时分（"秒级本地跑、分钟级进 CI"）的问题是**阈值会漂移**：机器换了、依赖变了、测试变多了，同一个测试就会从这一档滑到那一档，而没有任何人会去重新分类。

按测试对象分（单元 / 集成 / 端到端）的问题是**这三个词没有公认定义**。"集成测试"到底集成到哪一层，每个人的答案都不一样，于是分类争论永远不会收敛。

外部依赖是**物理事实**：这个测试要不要 Docker，要不要整套 compose，是能被一条命令验证的，不随人的理解变化。它同时天然决定了"能不能在本地随手跑"——这正是分档最实际的用途。

## 2. 准入规则解决的是"档位膨胀"

**能在上一档证明的事，不许放到下一档。**

这条规则针对的是测试套件最常见的腐烂路径：一个本该是纯函数测试的东西，因为"从 HTTP 打一下更省事"被塞进了端到端层。单个来看没问题，累积起来就是几百个慢测试，然后没人愿意在本地跑，然后这一档就死了——它还在 CI 里绿着，但已经不再提供任何反馈。

具体的例子：gRPC 错误码到 HTTP 状态码的映射（[D-19](../tasks/D-19-grpc-http-status-mapping.md)）是一张纯查表，它必须在 L1。用 HTTP 请求去验证它，是花 30 秒买一个 3 毫秒能得到的结论。

反过来这条规则也是**双向**的：只有下一档能证明的事，必须留在下一档。L3 存在的唯一理由就是这个——见第 5 节。

## 3. 为什么 L2 不用 seed 数据

现在的 pytest 全都寄生在 `flight-service/migrations/002_seed.up.sql` 的三行数据上：`tests/test_api.py` 把三个 UUID 和座位数抄成了常量，断言 `available_seats == 180`。这条耦合是**隐式的**——改一行 seed，一批测试静默变红，而 diff 里看不出因果。

更实际的问题是**并发**。所有测试共享同三行数据，意味着它们不能并行：两个测试同时打同一个航班，你分不清看到的是缺陷还是测试互相干扰。而"最后一个座位被两个人同时抢"（见 [`design/system-design.md`](../design/system-design.md) § 5.0）恰恰是这个系统最需要被测到的场景。

测试自己造数据还有一个可读性上的净收益：

```go
f := newFlight(t, db, withSeats(1))   // 这一行就说清了测试的前提
```

对比 `FLIGHT_SU1234` —— 你得翻到另一个文件才知道它有 180 个座位。**测试的前提条件写在别处，是可读性的净损失。**

## 4. 为什么两个服务各测各的

Go 的 `internal` 规则按**模块目录树**生效：`flight-service/internal/*` 只能被 `flight-service/` 树下的代码 import。`booking-service` 是平级的另一棵树，跨不过去——这不是风格选择，是编译错误：

```
use of internal package .../flight-service/internal/handler not allowed
```

所以"在 booking 的测试里起一个真实的 flight-service"这条路是封死的。替代方案是 booking 侧用 `pb.RegisterFlightServiceServer` 注册一个**测试桩**（`pb` 是公开的生成包）。

而这个限制反而指向了更好的设计。看一下 booking 侧那几条待验证的缺陷需要下游做什么：

| 缺陷 | 需要下游 | 真实服务能做到吗 |
|---|---|---|
| [D-25](../tasks/D-25-no-timeouts-anywhere.md) 无超时 | 接受连接但**永远不回包** | ❌ 得往它的 handler 里塞 sleep |
| [D-21](../tasks/D-21-half-open-no-probe-limit.md) HALF_OPEN 不限流 | 按脚本精确控制成功/失败序列 | ❌ 难以编排 |
| [D-19](../tasks/D-19-grpc-http-status-mapping.md) 状态码映射 | 按需返回**任意** gRPC code | ❌ 有些 code 真实实现根本不产生 |

**它们需要的不是"真实的对端"，是"可控的对端"。** 为了测 D-25 而往生产代码里加 sleep，是让测试污染实现。

代价是桩会和真实实现漂移——桩里写"座位不足返回 `RESOURCE_EXHAUSTED`"，真实服务哪天改了，booking 的 L2 全绿而线上炸。这个漏洞由 L3 补，见下一节。

## 5. L3（pytest）为什么还留着，以及它该测什么

L2 建成之后，`tests/test_e2e_db.py` 现在做的事（search → create → cancel + 双库断言）会被完整覆盖，而且更快。如果 L3 继续做同样的断言，它就只是一份跑得更慢的重复品。

L3 唯一不可替代的职责是**契约一致性**：真实的 flight-service 在每种业务场景下**实际**吐出什么 gRPC code、经过 booking-service 之后变成什么 HTTP status。这件事 L2 在物理上做不到——L2 里的下游是桩，桩说什么都算数。

这正是第 2 节那条规则的反向应用：**只有下一档能证明的事，必须留在下一档。**

（在此之前 L3 还有一个临时职责：给 [T-01](../tasks/T-01-extract-app-package.md) 的纯搬运重构当验收网。那次重构改的是装配结构、不改外部行为，而 L3 对内部结构一无所知、只看外部行为——正是这类重构最需要的那种测试。）

## 6. 为什么容量结论不能来自 CI

GitHub Actions 的标准 runner 是 2–4 核；开发机是 12 vCPU / 7.7 GiB，且要同时跑 13 个容器。**同一份 k6 脚本在两边跑，拐点位置差一个数量级。**

留着一个判不了真东西的门禁，比没有门禁更坏：它会训练你忽略红叉，而 `CLAUDE.md` § 1 明写「门禁可以被绕过就不再是门禁」。所以 CI 里的 k6 只回答"跑得起来、没崩、没有数量级退化"。

**容量数字必须本机手测**，且必须写进 [`reports/load/`](../reports/load/)——它无法自动化，唯一防止它失传的方式就是写下来。每份报告必须记录当时的机器配置，否则两份报告没法比。

## 7. 闭环压测测不出拐点

k6 默认的 VU 模式是**闭环**：发一个请求、等响应、再发下一个。系统一慢，VU 就跟着慢下来，发压速率自动降低——吞吐恒等于 `VU数 ÷ 平均延迟`，系统被"保护"着永远不会真正过载。

改造前 `k6/script.js` 里那个 `sleep(0.1)` 只是把天花板从 `10/延迟` 压到 `10/0.11`，**去掉它天花板变高，但它仍然是天花板**。

要看到排队效应（利用率过 70% 后延迟非线性恶化），必须用**开环**（`ramping-arrival-rate`）：按固定速率发压，不管系统回不回得过来，请求才会堆积，拐点才显形。

同理，混合配比的场景测不出任何单一上限——瓶颈永远是最先饱和的那条路，你只会知道"系统在 X QPS 时开始变慢"，不知道是谁先撑不住。所以读路径和单航班写路径必须**分开压**。

### 但闭环不是没用的，它测的是另一个数

闭环下 `VU数 = 吞吐 × 延迟` 是恒等式。饱和后吞吐顶死在 `X_max`，于是 `延迟 = VU数 ÷ X_max` —— **延迟随 VU 数严格线性增长**。这条性质有两个后果，方向相反：

- 闭环**给得出**吞吐平台有多高。加 VU 到吞吐不再涨，那个平台高度就是 `X_max`
- 闭环**给不出**过载后延迟怎么恶化。延迟只是 VU 数的线性函数，永远不会非线性起飞

根因是闭环里**需求依赖于容量**（系统慢了，VU 自动少发），而真实需求是独立的：3 万人抢票不会因为系统慢就少点几次。开环才是那个模型。

所以两个都要跑，且有顺序：**先闭环 `recon` 测出 `X_max`，再开环 `ladder` 自 `0.5×` 铺到 `1.5×X_max`**。

直接开环有两个具体的坑：

1. 阶梯范围只能靠推算，而推算正是压测要验证的东西——把结论当成了前提
2. 第一档就可能已经过载。这个系统过载后**不是快速失败、是慢慢卡死**（`design/system-design.md` § 5.1 的五步级联：等锁 → 无超时 → goroutine 与连接堆积 → 池耗尽 → 无响应），此后所有档测的都是一具尸体

第 2 条另配一道运行控制：开环跑的 `http_req_failed` 持续超过 50% 即 `abortOnFail` 中止（`k6/script.js:165`）。它是测量跑的保险，不是 SLO 门禁——阶梯本来就该压过拐点，把出错判成 fail 没有意义。

### 阶梯的数要按档看，不能看总 summary

k6 收尾的 summary 把拐点前后所有请求混在一起算一个 p95，那个数没有意义。`k6/analyze_ladder.py` 按档切开，每档给实际速率、p50/p95/p99、2xx/409/其他错误占比与状态码分布。

**状态码分布必须打出来，不能只看 409。** 本机实测过一次：写场景库存被压干后刷 409，而 409 洪水把熔断器打开（[D-01](../tasks/D-01-circuit-breaker-error-classification.md) 把业务错误计入失败统计），之后返回的全是 503。只盯 409 那一栏会完全看漏"这一档根本没测到行锁"。

## 8. 当前不覆盖什么

> **空洞写下来才是空洞，不写下来就是假的全绿。**
>
> 这一节是硬要求：任何一档做出"暂时不覆盖"的决定，都必须在这里留一行，写清楚为什么、以及什么条件下该补上。

| 空洞 | 为什么现在不覆盖 | 什么时候该补 |
|---|---|---|
| **Redis 真实行为**（Sentinel 故障切换、TTL 实际过期、连接中断） | L2 用内存假实现，只验证调用时序与失效逻辑，不验证 Redis 本身 | [D-04](../tasks/D-04-sentinel-quorum-ha.md) 修复时，或缓存策略变更时 |
| **跨库一致性缺口**（[D-06](../tasks/D-06-seat-inventory-leak.md) 库存泄漏） | 需要在 `ReserveSeats` 成功后、写 `bookings` 前**注入故障**，任何一档的常规测试都做不到 | 阶段 5 混沌场景 9 |
| **L1 大面积空白** | `service` / `repository` / `grpcclient` / `metrics` 目前几乎零单测；地基阶段只补被 T-03/T-04 牵动的部分 | 每修一条缺陷时按 TDD 增量补 |
| **迁移的 down 路径** | L2 永远用全新容器，只跑 up；`.down.sql` 文件本身尚不存在 | [D-28](../tasks/D-28-missing-down-migrations.md) |
| **指标与告警的实际触发** | `CLAUDE.md` § 4 要求"指标/告警要能实际触发一次"，当前只有 `scripts/demo_alerts.sh` 手工脚本，未纳入任何一档 | 阶段 4 SRE 方法论 |
| **认证与授权** | 系统当前没有认证（`user_id` 由客户端自填），没有东西可测 | 引入认证时 |
| **极高吞吐下"谁先饱和"分不清** | 压测机与被测服务同机。读路径闭环平台已到约 1.9 万 req/s，开环要压到约 2.8 万——单个 k6 进程很可能先于被测系统饱和，届时"跟不上目标速率"是 k6 的极限还是系统的极限，这台机器上分不开。判据只有 `MAX_VUS` 是否触顶与 `dropped_iterations` 的量 | 需要读路径的绝对容量数字时，得把压测机挪到另一台机器 |
| **绝对延迟数字** | 同上，测出来的延迟里混着压测机自己的排队。结论只能是"拐点在哪"，不能是"绝对延迟是多少" | 同上 |
