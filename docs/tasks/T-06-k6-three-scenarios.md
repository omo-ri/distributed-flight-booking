# T-06 k6 改造成三个场景，开环压测找拐点

**前置**：无。**本条不依赖地基阶段其他任何一条**，可以最先做——它通向这一轮唯一的真未知数。

## 为什么需要

当前脚本测不出任何有意义的容量数字，有三个独立原因：

1. **闭环压测测不出拐点**（理由见 [`conventions/testing.md`](../conventions/testing.md) § 7）。`k6/script.js:82` 的 `sleep(0.1)` + 10 VU，吞吐上限 ≈ 90 req/s 是 k6 自己的天花板；去掉 `sleep` 只是把天花板抬高，仍然是天花板
2. **混合配比测不出单一上限**。50% 搜索 / 40% 查详情 / 10% 下单的混合，瓶颈永远是最先饱和的那条路
3. **热点分散度不对**。`k6/script.js:19-23` 在 3 个航班里随机挑，而 [`design/system-design.md`](../design/system-design.md) § 1.3 的尖峰场景是 **2000 QPS 全部砸在 1 个航班上**——分散负载可以靠加机器解决，集中负载不行，这两件事测的不是同一个东西

## 做什么

三个场景，各自回答一个问题：

| 场景 | 打谁 | 回答什么 | 对应 |
|---|---|---|---|
| 平峰稳态 | 多航班，读写 20:1 混合，恒定 500 QPS | R2/R3 在正常态成立吗（p95 < 50ms、错误率 < 1%） | § 1.4 |
| 读路径 | 打散到多航班，只压 `GET /flights/{id}` | 2000–3000 QPS 这个推算对吗 | § 1.3 |
| 单航班写 | 锁定 1 个航班，只压 `POST /bookings` | 行锁上限真的是 300–1000 单/s 吗 | § 1.3、§ 5.1 |

第三个最有价值：设计文档整组假想规模都压在它上面，而"尖峰必然撞穿行锁上限"目前是**推算，不是测量**。

### 两个阶梯场景各有两种发压模式，必须按顺序跑

| | `MODE=recon`（闭环摸底） | `MODE=ladder`（开环突破） |
|---|---|---|
| executor | `ramping-vus` | `ramping-arrival-rate` |
| 阶梯轴 | VU 数递增 | 目标速率递增 |
| 读出什么 | 实际 req/s 在哪一档不再涨 = `X_max` | 实际 req/s 在哪一档追不上目标 + p99 何时起飞 |

**为什么需要 `recon` 这一步**：开环阶梯的范围必须来自实测。若直接照 § 1.3 的推算铺阶梯，等于把要验证的结论当成前提；更糟的是第一档就可能已经过载，而这个系统过载后**不是快速失败、是慢慢卡死**（§ 5.1 的五步级联：等锁 → 无超时 → 连接堆积 → 池耗尽 → 无响应），后续所有档测的都是一具尸体。

**流程**：先 `MODE=recon` 拿到 `X_max` → 用 `-e RATE_MAX=<1.5×X_max>` 跑 `MODE=ladder`，阶梯自 `0.5×X_max` 铺到 `1.5×X_max`，保证拐点两侧都有足够采样点。上界取 1.5 倍而非 1.0 倍，因为闭环测出的 `X_max` 通常略高于开环下的真实容量——高并发的调度开销在闭环里被 VU 自己吸收掉了。

**闭环与开环各自能回答什么，不能混为一谈**：闭环下 `VU数 = 吞吐 × 延迟` 是恒等式，饱和后吞吐顶死、延迟随 VU 数**严格线性**增长。所以闭环给得出「吞吐平台有多高」，给不出「超过容量后延迟怎么非线性恶化」——后者在闭环下物理上不可见（§ 7）。根因是闭环里需求依赖于容量（系统慢了 VU 就自动少发），而真实需求是独立的：3 万人抢票不会因为系统慢就少点几次。

**开环跑加一道运行控制**：`http_req_failed` 持续超过 50% 即 `abortOnFail` 中止，不再往一具尸体上加压。这是测量跑的保险，与平峰场景那三个真断言不是一回事。

**两处与初版设想的偏离**（定于开工前，理由记在这里）：

- **平峰场景用 `constant-arrival-rate` 而不是闭环 VU**。初版写的是"闭环"，但闭环的实际吞吐恒等于 `VU数 ÷ 延迟`——要凑到"约 500 QPS"得反复调 VU 与 `sleep`，且系统一变快数字就飘。这个场景的目的是"在**确定的** 500 QPS 下检查 SLO 成不成立"，速率必须钉死。闭环的缺陷只在找拐点时是致命的，这个场景不找拐点
- **读路径场景只压 `GET /flights/{id}`，不混 search**。§ 7 自己写了"混合配比测不出任何单一上限"：search 走 Postgres 路由查询返列表，getById 走缓存热点读，成本量级不同，混在一起瓶颈只反映慢的那条。search 由平峰场景按 20:1 覆盖

**两处口径修正**：

- **`http_req_failed` 必须排除 409**。`k6/script.js:35` 现在把它算作失败，而单航班场景下座位卖完刷 409 是**正常业务结果**（§ 3.3 明写）。用 `setResponseCallback` 排除——**这和 [D-02](./D-02-error-rate-sli-server-errors-only.md) 是同一个错误在压测侧的镜像**
- **写场景用大 `total_seats` 的专用航班**。单航班 300 座，开环压几秒就卖光，之后测的是"409 的吞吐量"。行锁竞争的是那**一行**，不是那个数字，把库存耗尽这个变量消掉，测出来的数才只反映锁

## 验收标准

**怎么验证它生效了**

- 三个场景能各自独立跑起来（`SCENARIO=steady|read|write`），两个阶梯场景的两种模式也能各自指定（`MODE=recon|ladder`）
- 单航班写场景在整个压测窗口内**不出现库存耗尽**：分析表里 409 占比恒为 0
- 错误率曲线里不含 409（`setResponseCallback` 把 409 排除出 `http_req_failed`）
- 阶梯场景能产出一张「速率 → 延迟」表，读路径的 `ladder` 跑里**能看到拐点**（实际 req/s 追不上目标 + p99 起飞），而不是一条平线

**怎么知道它出问题了**

- 分析表里 409 占比 > 0 → seed 没灌，或库存被压干，该跑的数没测到
- 实际 req/s 从第一档就追不上目标 → `maxVUs` 不够或压测机自己饱和，测的是 k6 不是系统
- `recon` 跑的吞吐从头到尾线性增长、没有平台 → 阶梯上界不够高，`X_max` 没找到

**怎么回滚**

- `git revert`；压测数据用 `docker compose down -v` 清掉
- 压测航班 ID 固定在 `00000000-0000-4000-8000-…` 段，与 seed 航班（`a0ee…` / `b0ee…` / `c0ee…`）不重叠，不影响现有 L3 pytest

## 注意事项

**压测专用航班怎么造，是个要想清楚的选择。** 走迁移会污染生产 schema 的 seed；走 API 造不出来（系统没有航班管理路径，见 § 1.1）。**结论：一段独立的 `k6/loadtest-seed.sql`，由 `make loadtest-seed` 灌入，不进 `flight-service/migrations/`。** 它是测试装置，不是系统的一部分，报告里须注明。

航班 ID 用**确定性 UUID**（读航班 `00000000-0000-4000-8000-0000000000NN`，写航班 `…-00000000ffff`），这样 k6 脚本自己算得出 ID，不必在 SQL 与 JS 之间传数据。

**这台机器上压测机和被测服务同机**，200+ VU 的 k6 会和 13 个容器抢 CPU。结论只能限定为"拐点在哪"，不能是"绝对延迟是多少"（§ 1.5 🔧 已经承认了这个边界）。

## 验证记录

机器：12 vCPU / 7.7 GiB，WSL2 + Docker，13 个容器同时在跑，压测机同机。

**已验证**

| 项 | 证据 |
|---|---|
| 库存被压干时测不到锁（红） | 把写航班库存改成 300 跑 `write/ladder`：4143 个请求里只有 300 个真下单，其余全是 503；分析表每档 `2xx% = 0`，并打出告警 |
| 409 确实被排除出 `http_req_failed` | 红跑的 CSV 里 409 那 5 条 `expected_response=true` |
| 库存足够时不再耗尽（绿） | 重灌 seed 后同一条命令：64999 个请求，每档 `2xx% = 100%`、`409% = 0`、`http_req_failed = 0` |
| `recon` 能测出吞吐平台 | `write/recon` 40→240 VU：吞吐 546→653→649→638→634，平台 `X_max ≈ 654`；延迟 63→119→184→248→318→389 ms，随 VU 严格线性（240 ÷ 654 = 367ms，实测 p50 389ms）——恒等式成立 |
| `ladder` 能看到拐点 | `write/ladder RATE_MAX=654`：目标 458 时 p50 = 14ms，目标 589 时实际只跑到 552、p50 = 846ms（60 倍跳变）；再往上**吞吐倒退**（目标 719 只跑到 527），`dropped_iterations = 34133` |
| 分析脚本的截断处理 | 红跑被 `abortOnFail` 拦腰截断，未做截断校正前会算出"实际 93.5 / 目标 200"的假拐点；按实际时间窗归一后回到 200.3，假拐点消失 |
| 压测数据不干扰 L3 | 压测航线是 `AAA→BBB` / `AAA→CCC`，pytest 只对 `SVO→LED`、`VKO→LED` 断言条数 |
| 分析脚本在 GB 级 CSV 上可用 | 读路径 4 分钟跑产出 8.4 GB CSV。原实现 `csv.DictReader` 逐行全解析要约 160s（超时）；改成先用 `startswith` 筛掉约 11/12 的非目标采样行后为 21s，同一份 209 MB 文件上输出逐字节一致（4.0s → 0.53s） |

**顺带测到的两件事**（都不是本条任务的范围，登记以免丢失）：

- **[D-01](./D-01-circuit-breaker-error-classification.md) 在负载下被实拍到**：座位卖光后的 409 洪水把熔断器打开，之后返回 503。这是"业务错误被计入失败统计"的直接后果，此前只有代码推断
- **[D-25](./D-25-no-timeouts-anywhere.md) 的前提被证实**：写路径压过拐点后，系统**完全不丢负载**——2xx 始终 100%，只是延迟涨到 2 秒。没有超时就没有快速失败，只有无限排队

**尚未验证**（`status` 因此仍是 `doing`）

- `steady` 场景**一次都没跑过**。它的 `constant-arrival-rate` 配置、`steadyMix()` 与 CI 那条烟雾跑都还没有被执行过
- `read/ladder` 没跑。读路径只跑了 `recon`（`X_max ≈ 18894 req/s`，比 § 1.3 推算的 2000–3000 高一个数量级），拐点曲线是在**写**路径上看到的，不是读路径
- CSV 改成 `.gz` 输出（`Makefile` 的 `run_k6`）后**还没跑过一次**。分析脚本的 `.gz` 读取路径本身是有的，但 k6 按扩展名自动压缩这件事在本机未经执行验证
- 这三条跑完才满足验收里的"三个场景能各自独立跑起来"与"读路径能看到拐点"

**已知限制：CSV 体积**

每个请求约产出 12 行采样，读路径一次 4 分钟的跑就是 8.4 GB 明文。已改为 `.gz` 输出缓解，但根子上是"把全部原始采样落盘再离线聚合"这个做法。**更好的解法**是在 k6 里按档打标签并预先声明 `http_req_duration{step:N}` 这组子指标，让 k6 自己算完百分位、由 `handleSummary` 直接吐出——完全不需要 CSV。没有现在就做，是因为它是一次拿不到验证机会的重写；等 [T-07](./T-07-local-capacity-baseline.md) 跑完整轮时一并考虑。

**注意**：`read/ladder` 要压到 `1.5 × 18894 ≈ 28000 req/s`，单个 k6 进程在这台机器上很可能先于被测系统饱和。那一跑要专门确认"跟不上目标"是系统的极限还是 k6 的极限——`MAX_VUS` 与 `dropped_iterations` 是判据。

## 学到什么

**闭环压测有一个反直觉的性质：它会保护被测系统。** VU 等响应，系统一慢发压就自动降速，于是你永远看不到过载——测出来的曲线平滑好看，却完全没有回答"它什么时候撑不住"。

**要观察排队，就必须让请求真的排队。** 这是开环和闭环的全部区别，也是"压测"和"跑一跑看看"的区别。

**但"闭环没用"是错的，它测的是另一个数。** 闭环给得出吞吐平台 `X_max`，给不出过载后的非线性恶化；开环反过来。直接开环有个具体的坑：阶梯范围只能靠推算，而推算正是压测要验证的东西。本次实测把这一点摆得很清楚——最初凭 § 1.3 推算给写路径定的 `RATE_MAX=200`，离实测的 654 差了三倍多，那一跑六档全部轻松跟上，什么也没测到。

**过载的表现比"变慢"更难看：吞吐会倒退。** 目标 719 req/s 时实际只跑到 527，低于目标 589 时的 552。加压反而更慢，这是排队系统的典型特征，也是闭环压测在数学上不可能显示出来的东西。
