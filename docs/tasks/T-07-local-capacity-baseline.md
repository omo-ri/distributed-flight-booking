# T-07 本机容量基线，产出可信的压测报告

**前置**：[T-06](./T-06-k6-three-scenarios.md)

## 为什么需要

**这个系统的吞吐上限从未被测过。** 唯一一次基线（[`reports/load/2026-05-29-baseline.md`](../reports/load/2026-05-29-baseline.md)）跑出 82.86 req/s，但那是 k6 自己的天花板；中位数 0.92ms 说明当时系统基本闲着。

它是这一轮唯一的**真未知数**——已知缺陷有 27 条且都带行号，再测一遍只会复现它们；而容量拐点在哪，没有任何文档能回答。

它同时是三条任务的前置：

```
T-07 可信基线 ──► D-27 直方图桶要按实测分布定（当前最小桶 5ms，实测中位数 0.92ms）
              ├──► D-25 超时值要由实测 p99 决定，不能拍脑袋
              └──► D-16 容量规划本身
```

## 做什么

在**开发机**上跑 [T-06](./T-06-k6-three-scenarios.md) 的三个场景，每个场景阶梯加压到出现拐点，产出一份 `docs/reports/load/YYYY-MM-DD-<名称>.md`。

报告至少包含：

- **机器配置**（CPU 核数、内存、同时运行的容器数）——没有这个，两份报告没法比
- 每个场景的速率-延迟曲线、拐点位置、拐点处的错误码分布
- **实测延迟分布的量级**（给 D-27 定桶用）和 p99（给 D-25 定超时用）
- 实测数字与 [`design/system-design.md`](../design/system-design.md) § 1.3 三条推算的对照：读路径 2000–3000 QPS、分散写 300–600 单/s、单航班写 300–1000 单/s

## 验收标准

- 三个场景各有一条能看到拐点的曲线
- 报告能回答："单航班下单的吞吐上限是多少，超过之后延迟怎么变"
- 报告能直接支撑 D-27 的桶边界选择和 D-25 的超时取值
- 文件写入 `docs/reports/load/`，**此后永不修改**（`CLAUDE.md` § 3：记录层只新增）

## 注意事项

**如果实测数字推翻了 § 1.3 的推算，不要改推算去迁就数字，也不要反过来。** 设计文档第 1 章明写那组规模是"假想"的、是推理起点。实测与推算的**差异本身**才是最有价值的产出——差在哪、为什么差，是下一轮设计决策的输入。

**压测机与被测服务同机**，测出来的延迟里混着压测机自己的排队。结论限定为"拐点在哪"，不写"绝对延迟是多少"。

## 学到什么

**"没测过"和"测过但数字不可信"是两种状态，后者更危险。** 前者你知道自己不知道；后者会让你拿着一个假数去做超时、桶边界、扩容决策，而且一路上没有任何东西提醒你。

`metrics-report.json` 里那个 4.86ms 就是这类数——它是真实测出来的，但测的是一个基本闲着的系统，拿它当容量依据会得出完全错误的结论。**一个数字的可信度，取决于产生它的实验设计，而不是取决于它是不是被真的测出来的。**
