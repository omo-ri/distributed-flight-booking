# 报告

**带日期的记录层文档。写完不改，只新增。**

## 为什么"写完不改"是硬规则

一份复盘写的是"当时我们以为是 X，后来发现是 Y"。事后回去把它改成"就是 Y"，就毁掉了这份文档全部的价值 —— 它记录的不只是结论，是**认知过程**。

同理，一份压测报告记录的是**那一次运行在那个环境下的真实数字**。改数字就等于伪造实验记录，后面所有基于它的推导都失去依据。

发现记录有错，**新写一份，并在旧文档里加一行指向新文档的链接**。

## 复盘文档要求

- **对事不对人**（blameless）。根因是"系统允许这种错误发生"，不是"某人手滑"
- 必须有**时间线**：故障开始 → 检测到 → 定位 → 缓解 → 恢复，每个时间点都有
- 必须有**量化影响**：多少请求失败、持续多久、错误预算消耗了多少
- 必须有**可执行的行动项**，每条对应一个 [`tasks/`](../tasks/README.md) 条目
- 必须写下**假设与现实的差异**

最后一条是演练报告里最有价值的部分。"我以为熔断器 5 秒内打开，实际用了 47 秒，因为窗口计数有个边界问题" —— 这种记录才说明演练真的做了。

演练的完整执行流程（写假设 → 注入 → 观测 → 恢复 → 对比 → 复盘 → 落实行动项 → 重新演练）见 [roadmap.md 阶段 5](../plans/roadmap.md)。

## 压测报告要求

- 记清楚**测试条件**：负载模型、时长、环境、镜像版本。条件不明的数字无法比较
- 同时记 **SLI 判定** 和 **k6 客户端侧原始数据** —— 两边口径不同，差异本身有信息量
- **异常必须写下来**，即使判定是 PASS。分位数按设计就会隐藏尾部
- 明确写出这份数据**不能**回答什么问题
