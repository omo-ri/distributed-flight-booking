# Dev

`CLAUDE.md` 是规则的唯一权威。这份文件不重复规则，只给**执行顺序**和**每一步的完成条件**；规则细节按需回查 `CLAUDE.md` 对应小节。

**验证优先于断言**贯穿全程：这份流程里每一句"已完成"都要能指到命令输出、文件路径或代码行号。

## 0. 分流

先判定这次改的是什么，它决定走哪几步、以及第 2 步拿什么当"红"：

| 改的是什么 | 走哪几步 | 第 2 步的「红」是 |
|---|---|---|
| **代码行为**：D-xx / T-xx / 新功能 | 1 → 6 | 一条能变红的测试 |
| **基础设施**：`docker-compose.yml`、`prometheus/`、`grafana/`、`alertmanager/`、`.github/workflows/`、`scripts/`、未来的 `deploy/` | 1 → 6 | 配置生效的可执行证据 |
| **纯文档**：补文档、修文档漂移、补 runbook | 5 → 6 | 无 |

纯文档那一档不建任务文件——`CLAUDE.md` § 1 把它划进"可以直接做"，给它套六步是拿流程办三分钟的事。

拿不准算哪一档，就问用户。

## 1. 任务

- 读 `CLAUDE.md` § 1。撞上「必须先问再动手」里的任何一条（新增服务或中间件、改数据模型、改 SLO 阈值、引入新框架/大依赖、跨阶段跳跃）→ 停下来问用户。
- 建立认知：`docs/architecture/overview.md` 定位改动范围；牵涉表结构读 `data-model.md`，牵涉接口与错误码读 `contracts.md`；想知道某个设计**为什么**是这样，读 `docs/design/system-design.md` 对应章节。
- 落到任务文件：已登记的缺陷直接打开 `docs/tasks/D-xx-*.md` / `T-xx-*.md`；新需求按 `docs/tasks/README.md` 的模板新建一个文件、分配 ID，并登进同页表格。
- 查 `docs/tasks/README.md` 底部的阻塞图。前置没做完就先说出来，让用户决定是补前置还是接受半截结论。
- 填满「验收标准」三问：怎么验证它生效了、怎么知道它出问题了、怎么回滚。
- `status: todo` → `doing`。

**⏸ 这一步末尾停下来**：把任务文件的改动范围和三问答案摆给用户，等他点头再进第 2 步。方案错了是最贵的错，这里是最便宜的纠错点。

**完成条件**：任务文件有 ID、三问答满且答案可核对；改动范围已列出，覆盖代码 / 契约（`proto/`、`booking-service/api/openapi.yaml`）/ 配置 / 指标与告警 / 测试档位 / 要同步的文档层；前置阻塞已确认；**用户已过目**。

## 2. 红

先有一条**能变红的测试**——本仓库判定"缺陷真实存在"的唯一方式（理由见 `docs/conventions/testing.md` § 2）。

- 定档：按准入规则选**最低**能证明它的那一档。能在 L1 用纯查表证明的，不要拿 HTTP 请求去验。
- 跑一次，亲眼看见它红，并确认红的理由就是任务文件里写的那个现象——不是编译失败，不是测试自己写错。

**基础设施改动的"红"是可执行证据**，同一条判据：没被执行过的东西不算数。

- 告警规则 → `promtool check rules` 通过，且照着 `scripts/demo_alerts.sh` 的路子**实际触发一次**，看见它在 Alertmanager 里出现
- CI 门禁 → 故意制造一次它该拦住的改动，看见 CI 变红
- compose / 部署清单 → `docker compose config` 渲染通过，起栈后目标端点可达
- 测试设施本身（T-01 ~ T-09）→ 用任务文件写的代替物（例：T-05 的"故意把构建标签拼错，CI 能红"）

**完成条件**：那条测试或那份证据已存在、已执行，且它红/它成立的理由与任务文件一致。

## 3. 开发

- 只做任务文件列出的范围。范围要变，先回第 1 步改任务文件。
- 契约是源：改 `proto/` 后跑 `make proto`；改 `booking-service/api/openapi.yaml` 后按 `booking-service/api/oapi-codegen.yaml` 重新生成。`*.pb.go` 与 `api.gen.go` 只由生成命令产出。
- 编码规范（配置分层、slog、指标命名与基数、告警的标签与注解）见 `CLAUDE.md` § 4。新增韧性机制必带指标——**没有指标的机制等于不存在**。

**完成条件**：改动文件清单与任务文件列出的范围一致；生成物由生成命令产出；新增机制带指标。

## 4. 验证

- 先让第 2 步那条测试变绿（基础设施改动：让那份证据从"能触发"变成"按预期触发"）。
- 再跑被改动牵动的档位。**命令以 `Makefile` 和 `.github/workflows/ci.yml` 为准**（当前 L1 = 两个模块各跑 `go test -race -count=1 ./...`，L3 = `make run` 起栈跑 pytest）。
- 容量结论只能来自本机压测，写进 `docs/reports/load/` 并记录机器配置。CI 上的 k6 是烟雾测试，判不了容量。
- 跑不绿就去修实现。**放宽 SLO 阈值、跳过测试、删断言都不算修。**

**完成条件**：那条测试变绿；L1 两个模块全绿；受影响的更高档已跑过并贴出输出；门禁与断言原样未动。

## 5. 归档

**做完不搬文件 = 没做完。** 按 `CLAUDE.md` § 3 的分层轴决定每份产出落在哪：

| 产出 | 落点 |
|---|---|
| 代码行为变了 | `docs/architecture/` 对应文件 |
| 新长出一项能力 | `docs/architecture/capabilities.md`，条目指到代码行号 |
| 任务做完 | `status: done` → 移进 `docs/tasks/done/` → 更新 `docs/tasks/README.md` 表格 |
| 新增告警 | `docs/runbooks/<告警名>.md`，文件名与告警名完全一致 |
| 压测数据 / 复盘 | `docs/reports/` 下**新增**一份，旧的不改 |
| 决定某块"暂时不覆盖" | `docs/conventions/testing.md` § 8 加一行 |
| 设计取舍或规模假设变了 | `docs/design/system-design.md` |
| 做法本身变了 | `docs/conventions/` 写理由，规则回 `CLAUDE.md` 改 |

**完成条件**：任务文件在 `done/` 里且 README 表格同步；受影响的文档与代码对得上（引用行号的要重新核对）；`docs/` 里没有留下描述"尚未实现的东西"的句子。

## 6. 提交

- 默认**不提交**：改动留在工作区供用户审查。
- 用户要求提交时：不在 `main` 上提交，按 `feat/` `fix/` `docs/` `chore/` 开分支；格式与类型表见 `CLAUDE.md` § 5；正文按需带 `Refs: D-xx`。
- 只有用户明确要求才 push 或建 PR。PR 描述写：改了什么、为什么、怎么验证的（贴第 4 步的输出）、有什么风险。**CI 全绿才合并。**

**完成条件**：改动已过第 4 步的验证并保留在工作区；如已提交，提交信息符合 `CLAUDE.md` § 5；如已 push，远端为最新且 CI 在跑。
